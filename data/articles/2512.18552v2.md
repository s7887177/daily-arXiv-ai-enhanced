# AI 程式設計師自學進化：讓模型在真實程式碼庫中自己出題、自己解題

> 原始論文：Toward Training Superintelligent Software Agents through Self-Play SWE-RL
> 作者·單位：Yuxiang Wei、Zhiqing Sun 等（Meta FAIR、伊利諾大學厄巴納-香檳分校、卡內基美隆大學）
> arXiv：2512.18552v2 ・ 分類：cs.SE / cs.AI / cs.CL / cs.LG

一句話說重點：不依賴任何人工標注的 Bug 報告或測試指令，只靠一個模型在真實程式碼庫中扮演「出題者」與「解題者」互相對弈，就能讓軟體工程 AI 代理人穩定自我提升，在 SWE-bench Verified 上進步 10.4 分。

---

## 背景：現在的 AI 程式設計師仍靠「人類出題」

近兩年，以大型語言模型（LLM）為核心的軟體工程代理人（Software Engineering Agent）進步神速，已能解決真實 GitHub Issue。但這些系統有一個共同瓶頸：訓練資料幾乎全依賴人類整理的問題描述、測試案例和程式碼審查記錄。

這意味著兩件事：第一，資料規模受限於人類能整理的量；第二，代理人學的是「重現人類解題過程」，而非「獨立發現新類型問題」。這條路走到盡頭，就難以突破人類能力上限，更遑論「超人工智慧」。

真正的問題是：能不能讓 AI 從零開始在程式碼庫裡自己創造學習素材？

## 怎麼做：一個模型，兩個角色，在程式碼裡自我對弈

**Self-play SWE-RL（SSR）**的核心設計是把同一個 LLM 分別扮演兩個角色：

**角色一：Bug 注入代理人（Bug-Injection Agent）**
給定一個真實的沙箱程式碼庫（只需要原始碼和已安裝的相依套件），代理人的任務是：
1. 選擇要破壞的目標程式碼行或函數。
2. 生成 `bug_inject.diff`：把 Bug 注入程式碼。
3. 生成 `test_weaken.diff`：削弱原有測試套件，讓這個 Bug 不會被原測試抓到。

Bug 的有效性必須通過「一致性檢核」：注入前測試通過、注入後特定測試失敗、削弱後測試重新通過——三步驗證確保 Bug 是真實且有意義的，而不只是語法錯誤。

**角色二：求解代理人（Solver Agent）**
拿到有 Bug 的程式碼庫，目標是生成修復 Patch（`pred_patch.diff`），讓原始測試套件重新通過。評估完全自動化：套用 Patch 後跑測試，測試通過即視為解題成功。

**強化學習訊號**：兩個角色共享同一組參數，用強化學習（RL）聯合訓練。Bug 注入的難度會隨訓練逐漸提升（課程學習），確保求解代理人始終面對適當挑戰而非瑣碎或不可能的任務。

一個關鍵細節：SSR **完全不使用自然語言 Issue 描述**——Bug 的規格書是測試套件的差異（test patch），這讓任務可從任意程式碼庫自動生成，無需任何人工標注。

## 結果：自我對弈勝過人工資料基準

在 SWE-bench Verified（500 個人工驗證的真實 GitHub Issue）和 SWE-Bench Pro（更難的進階基準）上：

- SSR 相比起始的 Code World Model（CWM-sft）基線，在 SWE-bench Verified 上從 41.0% 提升到 51.4%（**+10.4 分**）；在 SWE-Bench Pro 上從 21.1% 提升到 28.9%（**+7.8 分**）。
- 最重要的是：SSR 在**整個訓練過程中始終優於用人工資料做 RL 的基線**（CWM-sft + baseline RL，最終約 49.0%），說明自我生成的任務比人工整理的任務提供了更豐富的學習訊號。
- 儘管 SSR 訓練時從未見過自然語言 Issue 描述，評估時卻能成功解決這類問題，展現出良好的跨格式泛化能力。

消融實驗顯示，純「注入訓練」（只訓練出題能力）和純「修復訓練」（只訓練解題能力）都比完整 SSR 差，說明兩個角色的聯合自我對弈是效果的來源。

## 做不到的地方

- 目前 SSR 需要可沙箱化的程式碼庫（可執行、有相依套件可安裝），對許多缺乏完整執行環境的遺留系統適用性有限。
- Bug 注入代理人生成的 Bug 類型仍偏向「函數邏輯層面」的修改，較少涉及架構重構、效能問題或安全漏洞這類複雜問題。
- 評估仍使用 SWE-bench 這種以自然語言 Issue 為輸入的基準，訓練與評估的分布差異尚未完全消除。
- 論文呈現的是早期結果（標題也坦承是「first step」），距離真正「超越人類的軟體工程能力」仍有相當距離。

## 想自己判斷這篇可不可信？

| 訊號 | 這篇的情況 | 怎麼解讀 |
|---|---|---|
| 發表場合 | ICML 2026 正式論文 | 頂級機器學習會議，經過嚴格審查 |
| 評估基準 | SWE-bench Verified（人工驗證）+ SWE-Bench Pro | 業界公認的軟體工程 AI 評估標準 |
| 訓練資料假設 | 僅需沙箱程式碼庫，零人工標注 | 低資料假設是主要賣點，也是主要限制 |
| 來源機構 | Meta FAIR + UIUC | 工業界研究實驗室，資源充足但有商業利益考量 |
| 泛化性 | 訓練無自然語言描述、評估有 | 跨格式泛化成功，但仍需更多驗證 |

## 怎麼看這件事

「讓 AI 自己出題給自己做」聽起來像個悖論——出題者和解題者是同一個模型，訓練訊號從哪裡來？SSR 的答案是：**程式碼的可執行性提供了客觀的外部反饋**。測試跑不跑得過，不需要人類評判，這讓自我對弈的封閉迴路得以成立。

這個思路與 AlphaGo 的自我對弈有精神上的相似之處：不依賴人類棋局，只靠棋盤規則提供的勝負訊號。對軟體工程來說，「測試通過」就是那個客觀的勝負標準。能否把這個框架擴展到更複雜的軟體品質指標（效能、安全性、可維護性），是未來值得關注的方向。
