# 不裝第三方套件也能用：AI 幫你用 Python 內建函式庫重寫 40 個熱門套件

> 原始論文：Stdlib or Third-Party? Empirical Performance and Correctness of LLM-Assisted Zero-Dependency Python Libraries
> 作者·單位：Peng Ding、Rick Stevens（芝加哥大學、阿岡國家實驗室）
> arXiv：2605.21405v1 ・ 分類：cs.SE / cs.AI / cs.PL

一句話說重點：研究者用 LLM 協助把 40 多個熱門 Python 第三方套件重新實作成只用標準函式庫的單一檔案版，結果大多數在正確性和速度上都接近原版，但 C 擴充套件（影像處理、底層加密等）仍是無法逾越的效能牆。

---

## 問題的起點：一個 pip install 帶來的連鎖反應

每次在 Python 專案裡加一個外部套件，背後悄悄帶進來的東西遠不只那個套件本身。根據近年研究，宣告一個相依套件平均會觸發 8 到 10 個額外的傳遞性相依，而且其中超過七成的程式碼在實際執行時根本不會被用到。這造成三個問題：安裝時間長、版本衝突、供應鏈攻擊風險（你的程式碼沒問題，但你用的某個深層套件被植入惡意程式碼）。

一個長期存在的「解法」是「複製貼上」——把小工具套件的原始碼直接複製進專案，不加相依。但這個做法隨意、缺乏正確性保障、也沒有效能基準。

這篇論文的問題是：能不能系統性地、有紀律地把這件事做好？

## Zerodep 計畫：AI 輔助的零相依重寫

研究者建了一個叫做 **zerodep** 的開源套件集，規則很嚴格：
- 每個模組是**單一 Python 檔案**
- **只能用 Python 標準函式庫**（stdlib），不能 import 任何外部套件
- 必須做到與原套件的 API **介面相容**（drop-in 替換）
- 有**強制正確性驗證**：跑測試套件，對照原套件的輸出

開發流程是「人機協作循環」，共五步：指定目標套件 → LLM 生成初稿 → 跑自動測試驗證 → 效能評估 → 人工審查與版本更新。簡單的套件一到兩輪就完成，複雜的需要更多人工修正。

目前已完成 44 個模組，橫跨 12 個分類：網路協定、序列化（YAML/JSON/TOML）、密碼學、Agent 協定、文字處理、設定管理等。

## 核心發現：什麼情況下 stdlib 夠用

### 大多數情況：速度不差（2 倍以內算及格）

研究者把「效能相差 2 倍以內」定義為「相當（parity）」。測試結果顯示，**大多數類別的 zerodep 模組都在這個範圍內**。

更驚人的是，有幾個類別的 zerodep 版本**反而比原套件快**，倍率最高達 5 到 115 倍。原因不是 zerodep 更聰明，而是那些熱門套件背負了「通用框架的建構成本」——它們為了支援各種罕見用例加了很多層封裝，但對一般用法而言這些封裝是純粹的開銷。例如：
- `retry`（重試裝飾器）：zerodep 版快 5 倍以上
- `tabulate`（表格格式化）：zerodep 版快數十倍
- HTTP 客戶端的部分功能：架構開銷被消除後速度大幅提升

### 真正的效能牆：C 擴充套件

有三個類別是 stdlib 碰不到的：
- **影像處理**（PIL/Pillow）：底層 SIMD 優化的 C 程式碼，純 Python 慢一到兩個數量級
- **二進位序列化**（msgpack、protobuf）：C 擴充提供的解碼速度是純 Python 的 10 倍以上
- **底層密碼學**（PyNaCl、cryptography）：AES 硬體加速、橢圓曲線運算需要 C 實作

這個邊界很清楚：不是「純 Python 第三方套件 vs stdlib」，而是「有 C 擴充 vs 沒有 C 擴充」。

### YAML：意外發現

`yaml` 是測試中最特別的案例。zerodep 的純 Python YAML 解析器比 PyYAML 的純 Python 模式（不用 `libyaml` 的情況）快 7 倍。這表示 PyYAML 本身的純 Python 實作存在架構性效率問題，而 LLM 重寫恰好繞過了這些問題。

## 做不到的地方

- **API 相容性無法 100% 保證**：特別是帶有「有意省略的邊界條件」的套件，LLM 生成的實作可能在罕見輸入下行為不同；論文承認這些省略是有文件記錄的，但仍需謹慎。
- **C 擴充套件的效能差距無法靠純 Python 彌補**：這個限制是根本性的，不是工程技巧能解決的。
- **LLM 生成的程式碼需要人工審查才可信**：複雜功能（如 SMTP 協定、TLS 握手）LLM 初稿的可靠性仍需多輪迭代和人工修正。
- **測試覆蓋率有限**：測試集以「一般用法」為主，罕見邊界條件和深層 API 行為未必完全覆蓋。

## 怎麼看這件事

這篇論文的核心貢獻在於**提供了一張系統性的地圖**：哪些 Python 套件可以被 stdlib 替代、哪些不行、差多少。這個問題在嵌入式部署、邊緣計算、受限容器環境、供應鏈安全敏感的場景（例如政府、醫療、金融系統）中越來越重要。

更有趣的角度是：這篇論文實際上是在測試「LLM 能在嚴格符號約束下生成正確程式碼嗎？」——結果是「大多數時候可以，複雜情況需要人監督」。這對 AI 輔助開發（agentic coding）工具的邊界有直接的實踐意涵：讓 AI 幫你重寫一個網路小工具套件，大概 OK；讓它幫你重寫底層密碼學，請三思。
