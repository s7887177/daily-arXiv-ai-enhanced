# 用「多 AI 特工」把白話問題翻譯成 SQL 查詢：摩根大通的資料庫問答解法

> 原始論文：AgentNLQ: A General-Purpose Agent for Natural Language to SQL
> 作者·單位：Olena Bogdanov、Yeunji Jung、Chandra Dhir、Pareekshitreddy Gaddam、Saurabh Jain、Lakshmi Tumati、Vijay Parthasarathy、Anup Shirgaonkar（摩根大通 JPMorganChase）
> arXiv：2605.19010v1 ・ 分類：cs.AI

一句話說重點：摩根大通開發的多代理 NL2SQL（自然語言轉 SQL）系統 AgentNLQ，在業界標準基準 BIRD-SQL 上達到 78.1% 語意準確率，靠的是「預先用 LLM 替資料庫欄位寫豐富說明文件」加上「會自我反思、犯錯再試」的多代理編排器。

---

## 問題出在哪裡

企業裡絕大多數重要資料都存在關聯式資料庫中，但要從中取得答案需要撰寫 SQL——這是少數人才會的技術。「你幫我查一下上個季度哪些客戶購買了超過三次但退款金額低於 5%？」這種問題對分析師來說可能要寫幾十行複雜的 SQL，對一般業務人員根本無從下手。

大型語言模型（LLM）雖然能寫 SQL，但單次呼叫有三個硬傷：
1. **不知道你的資料庫長什麼樣**：表格名稱、欄位定義、外鍵關係都是企業特有的。
2. **不懂你的業務術語**：「客戶」在這個系統叫 `CUST_ID`，在那個表叫 `user_ref`。
3. **沒有自我修正能力**：寫出來的 SQL 語法錯了或邏輯不對，它不會自己重試。

現有的最好方法（黃金標準 SQL 專家手寫）在 BIRD 基準上能達到約 90% 準確率；單次 LLM 呼叫通常只有 50-60%。

## 怎麼做

AgentNLQ 把流程分成兩個階段：

**離線準備（只需做一次）**：
- **資料剖析器**：爬取資料庫，統計每個欄位的資料分布、空值比例、唯一值數量。
- **資料探測**：讓 LLM 自動理解各欄位在業務上的語意，識別外鍵關係與跨表聯結。
- **Schema 豐富化**：讓 LLM 幫每張資料表、每個欄位寫「人類可讀的語意說明」，建成向量索引。

**線上推論（每次問答觸發）**：
1. **實體抽取**：從用戶問題中辨識可能對應到欄位或值的關鍵詞。
2. **Schema 檢索**：根據實體做向量搜索，找出最相關的表格和欄位，注入給後續代理。
3. **多代理編排器**（核心創新）：
   - **快思路（System 1）**：先嘗試快速生成 SQL、執行、驗證，若成功就回傳。
   - **慢思路（System 2）**：若三次失敗，移交「SQL Author 代理」，從頭規劃、推導，並提供詳細推理鏈（Chain-of-Thought）。
   - 編排器會把 SQL 執行結果（成功則回傳數據，失敗則回傳錯誤訊息）作為反饋，進行自我反思和重試。

## 結果

- 在 BIRD-SQL 基準達到 **78.1%** 語意準確率。
- Schema 豐富化是最重要的單一貢獻：即使沒有 few-shot 範例，僅靠豐富化的 schema 說明就能顯著提升準確率。
- 自製的 NL2SQL 專屬編排器比通用的 Autogen Magnetic-One 編排器準確率更高、延遲更低。
- 向量搜索在大型 schema（超過 LLM 上下文長度）下顯著防止準確率下降。

## 做不到的地方

- 78.1% 在 BIRD 排行榜中並非最高（頂尖方法已超過 85%），差距源於沒有使用集成投票（ensemble voting）或大量 few-shot 範例。
- 系統每次推論都需要多次 LLM 呼叫（規劃、生成、驗證、自我修正），延遲和費用比單次呼叫高出許多，不適合低延遲場景。
- 評估基準（BIRD-SQL）提供了整齊的 schema 說明，現實中企業資料庫往往連基本文件都沒有，豐富化步驟的實際效果需要進一步驗證。

## 怎麼看這件事

讓非技術人員直接問資料庫「白話文問題」是許多企業夢寐以求的能力。AgentNLQ 的技術路線——靠豐富化 schema 彌補 LLM 對企業知識的盲點，靠多代理自我修正提升準確率——代表了工業界目前的主流做法，而非研究前沿的突破。

最值得關注的部分或許是「預先替資料庫欄位寫語意說明」這個步驟：投入一次性的 LLM 呼叫整理文件，換來長期的查詢準確率提升，這對資料工程師和分析師都是一個直接可採用的實務啟發。
