# 程式碼堆了好幾年，還找得回系統架構嗎？AI 替機器人軟體「逆向還原設計圖」

> 原始論文：Towards LLM-Assisted Architecture Recovery for Real-World ROS 2 Systems: An Agent-Based Multi-Level Approach to Hierarchical Structural Architecture Reconstruction
> 作者·單位：Dominique Briechle 等八位作者（克勞斯塔爾工業大學軟體與系統工程研究所，德國）
> arXiv：2605.20055v1 ・ 分類：cs.SE / cs.AI / cs.RO

一句話說重點：用大語言模型（LLM）搭配多層次中間表示，從 ROS 2 機器人系統的原始碼和啟動檔中自動「逆向還原」階層式架構圖，解決長期困擾機器人工程師的「架構圖一直跟不上程式碼」問題。

---

## 軟體老了，設計圖不見了

機器人系統通常是數十個甚至上百個程式節點（node）協同運作的複雜系統。理論上應該有一份系統架構圖，清楚說明哪個模組負責什麼、怎麼互相溝通。但在現實中，架構圖經常在第一週寫完之後就開始過時——程式不停更新，設計圖沒人維護。

**ROS 2**（Robot Operating System 2）是目前最主流的機器人軟體框架，但它的架構資訊偏偏分散在各種地方：有的在原始碼裡、有的在啟動檔（launch files）、有的在設定檔，還有命名空間（namespace）和參數映射（remapping）等複雜的動態行為。要手動把這些資訊整理成架構圖，非常耗費人力。

這篇論文的目標就是：**讓 AI 自動做這件事**。

## 分階段「逆向」的方法

研究者提出的系統叫做「Blueprint-Guided LLM-Assisted Architecture Recovery」（基於藍圖引導的 LLM 輔助架構還原）。核心思路是分三層逐步建構：

1. **節點分析（NodeAnalyzer）**：先從原始碼中確認所有「原子 ROS 節點」的清單與它們各自的通訊介面（話題、服務等），這部分靠確定性的靜態分析完成，不交給 LLM 猜。
2. **元件架構合成（ComponentArchitectureTeam）**：把節點清單和啟動檔的依賴關係交給 LLM，要求它合成「元件層次」的架構模型，包括命名空間和映射關係。
3. **系統架構合成（SystemArchitectureTeam）**：在元件模型基礎上，再讓 LLM 合成跨元件的系統層次結構，形成最終的完整架構圖。

關鍵在於：**每一步都有明確的中間產物**，後一步只在前一步的結果上工作，而不是讓 LLM 直接從原始碼猜出整個系統。這大幅減少了 LLM 的幻覺（fabrication）問題。

最終輸出是 PlantUML 格式的架構圖，可以直接渲染成視覺化的 PNG 圖片。

## 在真實機器人系統上的測試

研究者把這套方法應用在一個真實的「自動化產品拆解系統」上——兩台協作機械臂加上各種感測器和 ROS 2 模組，複雜度比他們之前發表的研究高很多。

結果是：與前一版方法相比，新方法在結構一致性（architectural consistency）、可擴展性（scalability）和穩健性（robustness）上都有改善。模型不再那麼容易在複雜的 launch 檔依賴關係中迷路。

## 做不到的地方

- **動態整合語意（dynamic integration semantics）**仍然是主要挑戰：有些節點的命名空間是在執行時動態決定的，靜態分析無法完全捕捉，LLM 也無法從原始碼推斷。
- 評估缺乏量化基準：論文主要靠定性描述說明改善，沒有精確的 recall/precision 數字。
- 系統依賴外部 LLM API（論文未指定模型），這意味著結果可重現性和 LLM 版本強綁定。
- 方法在單一案例研究上評估，通用性待驗證。

## 怎麼看這件事

機器人系統的架構文件問題在業界確實普遍存在，這個研究方向有明確的實際需求。分階段建構中間表示的思路——先確定性分析、再 LLM 合成——比直接讓 LLM 「猜整張圖」更可靠，也更符合軟體工程的最佳實踐。

不過這篇論文的最大問題是評估規模太小。單一案例研究加上定性描述，很難判斷這個方法在其他 ROS 2 系統上是否同樣有效。如果研究者能在多個開源 ROS 2 專案上提供量化的架構還原準確度，說服力會強很多。
