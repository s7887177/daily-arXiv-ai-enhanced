# 你說「我要一個交易後端」，AI 組了 6 個資料庫，第一次就跑起來了

> 原始論文：Declarative Data Services: Structured Agentic Discovery for Composing Data Systems
> 作者·單位：Shanshan Ye（Northeastern University）、Duo Lu（Brown University）
> arXiv：2605.20690v1 ・ 分類：cs.AI

一句話說重點：讓 AI 幫你挑選並串起 Kafka、ClickHouse、PostgreSQL、Redis 等多個資料庫系統的框架——比起讓 AI agent 自由發揮亂試，加上四層「型別合約」後成功率從 2/10 跳到 10/10，而且花費只有前者的三分之一。

---

## 問題：叫 AI 幫你建資料管線，它老是收斂不了

想像你是一個小型量化交易團隊，需要同時處理「每秒 5 萬筆報價的串流」、「多年歷史 OHLCV 資料的分析查詢」和「毫秒級的持倉查詢」，預算還只有每月 300 美元。你要選哪些資料庫？怎麼把它們接在一起？每個系統的版本限制、連接器怪癖又是什麼？

最直觀的做法：丟給 AI coding agent（比如 Claude Code），讓它邊試邊改。論文作者實際測試了這條路：讓 AI 迭代 5 次、每次把錯誤訊息餵回去，10 次嘗試中只有 2 次成功讓所有服務啟動（T1 通過率 2/10）。更慘的是有一次 AI 在第二輪把一個「已經跑起來的 stack」整個重寫，改出問題後再也修不回來。

問題的根源在於：**搜尋空間太大、驗證器只告訴你「失敗了」卻不說是哪個決策出錯**。

## 他們怎麼做

研究者提出「宣告式資料服務」（Declarative Data Services，DDS）：在 AI agent 和最終部署之間加一層結構性框架，把「建立一個多系統後端」這個大問題切成四個有型別約束的子問題。

**四層架構各司其職：**

- **L1 意圖層**：把自然語言需求轉成有型別的規格（資料模型、存取模式、規模、延遲、一致性、成本六個維度），防止 AI 在需求還沒確定時就開始寫程式碼。
- **L2 邏輯拓撲層**：先決定「要 INGEST → QUEUE → STORE → SERVE 這樣的架構」，再選具體產品，這樣拓撲錯了就在這層修，不會把下游全部推倒重來。
- **L3 實體技能層**：每個資料庫系統有一份「技能 YAML」，記錄它的能力、和其他系統的組合規則、禁忌（anti-patterns）。這份 YAML 是持久的記憶——某個版本的 ClickHouse 不支援在 DateTime64 欄位上設 TTL？記下來，下次部署自動帶著這條知識。
- **L4 執行歸因層**：部署失敗後，分類信號（port conflict → L3 技能補丁；拓撲 SLO 不達標 → L2 修正；用戶需求矛盾 → L1 修正），把錯誤路由到「擁有那個決策」的層，而不是讓 AI 在全域空間重新亂猜。

## 結果

同樣的 Claude 模型、同樣的工具、同樣的 5 次迭代上限：

| 條件 | T1（全服務啟動）| T2（煙霧測試通過）| 中位花費 |
|---|---|---|---|
| 純 AI agent 自由發揮 | 2/10 | 2/10 | $5.76 |
| 加上系統名稱提示 | 3/10 | 2/10 | $6.23 |
| 把技能 YAML 貼進 prompt | 6/10 | 4/10 | $5.06 |
| DDS（四層框架 + 5 次迭代）| 10/10 | 10/10 | $1.94 |

DDS 也實際接上 Coinbase 公開 WebSocket 資料跑了 10 分鐘，平均每秒 15.9 筆交易，端到端延遲 p50 約 3 秒、p95 約 4.7 秒。

## 圖解：四層架構如何分工

![DDS 的四層架構示意圖。左側是用戶輸入意圖（L0-L1），中間的框架把意圖轉成拓撲（L2）再選產品（L3），最外圈的 L4 歸因迴圈負責把執行錯誤路由回正確的層。](assets/articles/2605.20690v1-fig1.webp)

圖中最外圍的橘色虛線框是「L4 歸因迴圈」。左下角的對話泡泡代表用戶說「我要一個交易後端，50K ticks/sec，預算 $300」——這是 L1 意圖層的輸入。右上的 L2 方塊定義了邏輯拓撲（INGEST → QUEUE → STORE → SERVE），右下的 L3 方塊則是具體產品（Kafka、ClickHouse、FastAPI）。最中間的「Attributor」模組扮演裁判：當 L4 部署出錯，它決定這個錯誤要送回 L1（用戶修需求）、L2（換拓撲）還是 L3（修技能 YAML）。這個路由讓每次迭代只改一層，而不是全部重頭來過。

## 它做不到的地方

- 評估只在一個交易後端場景和 Claude Opus 4.6 一個模型上做，跨領域、跨模型的驗證還沒有。
- 實際負載（聲稱 100 events/sec）的 SLO 驗證被推遲到未來的「L5 評估層」，目前只有公開 feed 的輕量測試。
- 錯誤分類規則是手寫的，對未見過的故障類型的誤判率未知。
- 每次跑框架本身需要額外的 token 消耗（雖然比 baseline 便宜得多）。

## 想自己判斷這篇可不可信？

| 訊號 | 這篇的情況 | 怎麼解讀 |
|---|---|---|
| 作者／單位 | Northeastern University + Brown University 各一人，equal contribution | 兩人小組的早期原型，非大實驗室背書 |
| 發表狀態 | arXiv v1 預印本，尚無同儕審查 | 結果要保留懷疑 |
| 實驗規模 | n=10 runs per condition | 樣本不大，variance 可觀；部分結果可能被幾個幸運/倒霉的 run 左右 |
| 比較基準 | 只比「同一個 Claude 模型的不同使用方式」，沒比其他框架 | 沒跟 OpenDevin、SWE-bench 之類的 agentic 框架正面比較 |
| 程式碼開源 | 論文未提供公開程式碼連結 | 無法自行重現 |
| 用詞誠實度 | 明確列出「proof of life」、「early prototype」，主動指出未驗證部分 | 謹慎的自我定位，加分 |

## 怎麼看這件事

**為什麼有意思？** 這篇解決的不是「AI 能不能寫程式碼」（能），而是「AI 在一個複雜、多系統的搜尋空間裡能不能收斂」（通常不行）。把問題拆成有型別的子問題，讓錯誤可以被歸因到「是哪個決策出的問題」，這個思路本身比具體的系統選擇更有參考價值。

**哪裡要保留？** n=10 的實驗規模，加上只測了一個模型和一個場景，讓結果很難類推。技能 YAML 的撰寫和維護本身也是成本——論文裡的四份 YAML 是作者手寫的，在新領域冷啟動的代價沒有被計算進去。

**更廣的背景：** 這篇呼應了「AI agent 的可靠性不是靠更強的模型，而是靠更好的框架設計」這個越來越主流的觀點。當 AI coding 工具開始被用在「讓多個服務真正跑起來」而非「生成單一程式碼檔案」，這類結構性框架的需求會越來越真實。
