# 同一批 GPU 有快有慢，AI 模型怎麼聰明分配工作？

> 原始論文：GEM: GPU-Variability-Aware Expert to GPU Mapping for MoE Systems
> 作者·單位：Sourish Wawdhane、Avinash Kumar、Poulami Das（德州大學奧斯汀分校）
> arXiv：2605.19945v1 ・ 分類：cs.DC / cs.AI / cs.CL

一句話說重點：一批 GPU 跑混合專家模型時，最慢的那張卡決定整體速度——這篇論文考量了 GPU 硬體的速度差異，重新安排哪個專家放哪張卡，平均減少 7.9% 延遲，最高可達 16.5%。

---

## 混合專家模型的關鍵瓶頸

近年 AI 模型越來越大，但聰明的架構設計讓計算成本沒有等比例增長。「混合專家（Mixture-of-Experts, MoE）」就是這樣一個設計：不是每個 token 都走全部的神經網路，而是分成許多「專家（expert）」子網路，每次只啟動其中一小部分。例如 Mixtral 8x7B 有 8 個專家，每個 token 只啟動 2 個，計算量比同等大小的密集模型少約 5 倍。

在部署時，專家分散在多張 GPU 上。路由器（router）根據輸入 token 決定「送去哪張 GPU 的哪個專家」。但系統必須等整批 token 都處理完，才能進入下一層——這叫「鎖步執行（lock-step execution）」。一旦某張 GPU 跑得比較慢，其他 GPU 都要等它，它就成了瓶頸（straggler）。

## 被忽視的問題：GPU 速度本來就不一樣

現有研究試圖讓每張 GPU 處理差不多等量的 token，以此平衡負載。但這個思路忽略了一個現實：**「同型號的 GPU 速度本來就有差異」**。

製程變異、溫度、電源管理策略等因素，會讓同一批採購的 GPU 在吞吐量上相差不少。作者實測 128 張 NVIDIA L40 GPU，發現最快和最慢之間的差距達 27.7%；就算在同一台 8-GPU 伺服器內，一週內的速度差也有 7.7%。

傳統的「等量分配」做法，可能把用量最大的專家剛好放在最慢的那張 GPU 上，完全抵消了平衡的效果。

## GEM 的兩個洞察

論文提出 GEM（GPU-Variability-aware Expert Mapping）框架，核心思路分兩步。

**第一步：辨別「穩定型」和「臨時型」專家。** 分析 token 的使用分布後，作者發現專家分成兩類：**穩定型（consistent）**，幾乎每次都會被呼叫，使用率高而穩定；**臨時型（temporal）**，使用率低但往往同時啟動（某些任務類型才會一起出現）。

**第二步：聰明分配。** 穩定型專家是常態負載，臨時型是尖峰負載。關鍵規則：不要把「同一時間會一起被呼叫的穩定型和臨時型專家」放在同一張 GPU——這樣當臨時型被觸發時不會造成單卡過載。同時，避免把高使用率專家放在最慢的 GPU 上。

GEM 的四步流程：蒐集每個專家在線上推論時的 token 負載分布 → 為每張 GPU 建立效能變異檔案（latency vs. token load 曲線）→ 偵測穩定型和臨時型專家的組合 → 跑最佳化演算法把專家對應到 GPU，讓各卡的處理時間盡量齊平。

## 效果

在五種 MoE 模型（包含 Qwen3-235B）和三個任務集上，GEM 相對於現有基線（FasterMoE）平均降低端到端延遲 7.9%，在最佳情況下可達 16.5%。

注意這是在「不改模型精度、不改架構、不需重新訓練」的前提下達成的——純粹靠調整專家在 GPU 上的分配位置。

## 做不到的地方

GEM 需要離線做「準備工作」：蒐集每個 GPU 的效能檔案以及每個專家的使用分布，這代表部署前需要額外的剖析（profiling）步驟，而且換了不同的查詢任務或工作量後可能需要重新剖析。論文的實驗集中在數個常見模型，對更多種 MoE 設計（如 DeepSeek-V3 的細粒度路由）的通用性未完整驗證。另外 7.9% 的平均延遲改善算是適中，在部分場景下效益可能不大。

## 怎麼看這件事

這篇論文解決的是一個在系統工程裡容易被忽視的問題：硬體不是完全理想的。GPU 速度有差異這件事在雲端工程師中是常識，但 AI 模型部署的相關研究往往假設所有 GPU 等速。GEM 的貢獻是把這個現實納入 MoE 模型的專家分配問題，思路直接而有效。

值得注意的是，7.9% 的平均延遲改善聽起來不多，但在大規模生產服務中，每節省一點延遲都直接換算成伺服器成本和用戶體驗。這類工程優化論文的價值往往不在學術新奇性，而在真實可部署性。
