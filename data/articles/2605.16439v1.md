# 圖片看 AI 太吃記憶體？這招把畫面「壓縮存放、要用再還原」

> 原始論文：KVCapsule: Efficient Sequential KV Cache Compression for Vision-Language Models with Asymmetric Redundancy
> 作者·單位：Yingbing Huang、Deming Chen（伊利諾大學厄巴納-香檳分校）；Tharun Adithya Srikrishnan、Steven K. Reinhardt（AMD）
> arXiv：2605.16439v1 ・ 分類：cs.CV

一句話說重點：能同時看圖又看字的 AI 模型，處理圖片時會佔用大量顯示卡記憶體；這篇提出的方法把圖片的中間運算結果「壓縮存起來、需要算的時候再還原」，記憶體省到 2.4 分之一、速度快到 2 倍，準確率幾乎不掉。

---

## 背景／問題：圖片把 AI 的記憶體吃光了

現在很多 AI 不只能讀文字，還能看圖片，這類模型叫「視覺-語言模型」（VLM，Vision-Language Model）——像看圖說故事、看圖回答問題、多輪圖文對話都靠它。

問題出在它生成回答的方式：這類模型是「自回歸解碼」，一個字一個字往下產生，過程中必須一直把前面所有內容的中間運算結果存在一個叫「KV 快取」（key-value cache，鍵-值快取）的地方。文字還好，**一張圖片通常會被拆成幾百甚至上千個「視覺 token」**（模型處理的最小單位），所以只要幾張圖，就能把上下文撐得超長、瞬間吃光顯示卡記憶體。在多圖比較、影片理解（靠抽影格）、多輪圖文對話這種真實場景裡，視覺 token 會主宰整個輸入並一路佔著記憶體不放。

過去有人試著壓縮這個快取，常見做法是「根據注意力分數，把不重要的 token 直接刪掉」。但作者發現：這個假設是從純文字模型借來的，**對圖片不成立**。他們的實證分析揭露三件事：

1. **視覺 token 有大量「序列冗餘」**——畫面有空間連續性，相鄰區塊的資訊很重複，而且序列越長冗餘越多。
2. **哪些 token 重要會「動態變化」**——不同層、不同注意力頭、生成過程的不同步驟，關注的圖像區域都不一樣。實測顯示，生成初期最受關注的那批 token，跟第 5、10 步重疊只有 0.16；一開始被忽略的 token，後面可能突然變重要。所以「一開始就永久刪掉」很危險，刪掉就回不來了。
3. **鍵和值的冗餘不對稱**——「鍵」（key）之間相似度很高（尤其淺層），「值」（value）則比較各有各的內容。代表這兩者不該用同一套方法壓。

## 怎麼做：不刪資料，而是「壓縮存、用時還原」，且鍵值分開處理

作者提出 KVCapsule（KV 膠囊）。核心理念是：**不要永久刪掉任何 token，改成把整段視覺 KV 壓縮成精簡表示存起來，要做注意力運算時再還原成完整長度**。這樣記憶體省了，但模型仍能隨著「哪些 token 重要」的變化而靈活調整——因為資訊沒被丟掉，只是被壓著。

關鍵的「不對稱」設計是這篇的精髓：

- **鍵（key）**：因為鍵之間高度重複，只保留一小撮有代表性的鍵，再用一個輕量的兩層小網路（MLP）把完整鍵序列重建出來。鍵決定注意力權重，這樣能保住「注意力幾何」。
- **值（value）**：值各有各的語意內容，不能挑著刪。改用 PCA（主成分分析，一種抓出資料主要變化方向的數學工具）沿序列維度壓縮——讓「所有 token 都對壓縮表示有貢獻」，而不是整列丟掉。

此外，淺層的壓縮錯誤會一路傳到後面很多層，所以採用「金字塔保留策略」：淺層保留多一點資訊、深層壓得更狠。整套設計**不動原模型骨幹、不改注意力模組、不用重新訓練**，只加掛輕量的壓縮/還原元件。論文還提出「融合版」，把還原步驟直接整合進解碼時的注意力運算，避免顯式地把完整 KV 攤開來，進一步降低延遲。

這張圖把「壓縮存、用時還原」兩個階段一次講完。上半段是存的時候：原本要把每張圖的全部 KV 都塞進記憶體（灰色流程），KVCapsule 改成鍵只留代表（橘色「Apply to Keys」）、值做 PCA（「PCA to Values」），結果是一段短很多的「壓縮 KV」進記憶體。下半段是用的時候：把壓縮的 KV 取回，透過共享的鍵/值重建矩陣還原成完整序列，再交給原本的注意力模組。重點訊息：資訊沒被永久丟棄，只是被壓著，要算才還原——所以模型仍能隨生成過程動態調整關注哪些畫面區域。

## 結果：記憶體省到 2.4 分之一、速度 2 倍，準確率幾乎不掉

作者在 5 種主流 VLM 骨幹（Qwen2/2.5/3-VL、兩個 LLaVA 變體）與多個圖像/影片基準上測試：

- **準確率幾乎不掉**：在感知、推理、看圖說明、指令遵循、抗幻覺、多圖理解等任務上，KVCapsule 的成績都很貼近「完整快取」的基準。相比之下，「直接刪 token」的方法（如 FastV）在某些模型上會崩盤（例如 Qwen2.5 的 MME 從 1685 掉到 155）。
- **影片任務同樣穩**：短、中、長影片輸入下都接近完整快取基準，比剪枝法在動態視覺情境下更穩定。
- **效率**：在約 60% 的視覺 KV 壓縮比下，達到最多 2 倍的 TPS（每秒 token 數）提升與 2.4 倍的常駐記憶體縮減；批次大小為 1 時，9K-15K 長輸入的每 token 延遲降低 5.8%-25.8%（輸入越長省越多）。

## 做不到的地方：短上下文反而不划算

作者誠實點出限制。KVCapsule 加掛的「固定重建網路與 PCA 參數」本身有固定開銷，所以**好處只有在視覺上下文夠長時才會顯現**——論文算出一個「損益平衡點」約在 626 個 token，輸入比這短時，省下的快取還不夠抵銷重建元件的額外開銷，反而不划算。另外作者也說，他們目前是 PyTorch 層級的實作，若改用優化過的服務端核心（serving kernel），效率還有進一步提升空間（言下之意是目前的數字尚非極限、也尚未在生產級推論引擎上驗證）。本文的優勢明確聚焦在「長上下文、多圖」這個場景。

## 怎麼看這件事

**為什麼值得在意？** 「能看圖的 AI 太吃記憶體」是讓多圖、長影片、長對話這類應用難以普及的真實瓶頸。這篇最有價值的地方不只是省記憶體的數字，而是它先用實證指出「文字那套壓縮法用在圖片上會出問題」（重要性會動態變化、刪了回不來），再對症下藥用「可還原、不刪除、鍵值分開」的設計繞開這個坑。

**哪裡該保留懷疑？** 這是未經同儕審查的預印本；它的好處明確只在「上下文夠長」時成立，短輸入反而不划算；而且作者自陳目前是 PyTorch 實作、尚未在優化過的生產推論引擎上驗證——所以「2 倍速、省 2.4 倍記憶體」這些數字適用的是特定長上下文場景，不該無條件外推。

**怎麼理解這個研究方向？** 這屬於「讓大模型推論更省、更便宜」這條工程主線下，專門針對「多模態」的分支。它的洞見有普適性：當我們把為文字設計的優化手段直接搬到圖像/影片時，常會踩到模態差異的坑。KVCapsule 示範了一條務實路徑——先量測模態本身的結構特性，再據此設計「結構感知」的壓縮，而不是沿用文字模型的假設。
