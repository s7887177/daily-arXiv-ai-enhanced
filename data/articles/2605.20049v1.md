# 程式碼寫得乾淨，AI 幫你改的時候花的錢少三成

> 原始論文：Does Code Cleanliness Affect Coding Agents? A Controlled Minimal-Pair Study
> 作者·單位：Priyansh Trivedi, Olivier Schmitt（SonarSource）
> arXiv：2605.20049v1 ・ 分類：cs.SE / cs.AI

一句話說重點：「程式碼整不整潔」不影響 AI 編程代理完成任務的成功率，但乾淨的程式碼讓代理少用 7-8% 的詞元、檔案重複瀏覽次數減少 34%，直接影響 AI 使用的計算成本。

---

## AI 幫你改程式碼，費用誰決定？

2026 年，GitHub 的調查顯示已有約四分之一的開源專案出現了 AI 代理的足跡。用 Claude Code 或類似工具解一個軟體任務，光是輸入/輸出的詞元費用平均就要處理數百萬個詞元。

過去評估 AI 編程代理主要看「能不能完成任務」（通過率），很少有人問：**被改的程式碼本身的品質，會影響代理的工作效率嗎？**

這篇論文直接在相同任務、相同代理的條件下，把「程式碼是否整潔」作為唯一變數來測試。

## 最小配對實驗設計

要比較整潔與雜亂程式碼，就需要兩份「除了整潔度其他完全一樣」的程式碼庫——但現實中不存在這樣的資料。研究者從 SonarSource（靜態程式碼分析工具的製造商）出發，自行建構了六對**最小配對（minimal pairs）**倉儲：

- 每對倉儲的架構、相依套件、外部行為、測試完全相同
- 一份版本符合靜態分析規範（低認知複雜度、命名清晰、無壞味道）；另一份版本人工「污染」為有規範違規（或反向整理）
- 在六對倉儲上共設計了 33 個任務，透過隱藏測試驗證代理是否完成

使用 **Claude Code（Sonnet 4.6 模型）** 進行 660 次試驗。

## 主要發現

**任務成功率：幾乎沒有差異。** 代理在乾淨和雜亂的程式碼上通過率相似，說明整潔度不影響 AI「能不能做到」這件事。

**但操作足跡差異顯著：**
- 輸入詞元數：在乾淨程式碼上少 **7–8%**
- 輸出詞元數：同樣少 **7–8%**
- 檔案重複瀏覽次數（file revisitations）：少 **34%**

也就是說，面對雜亂程式碼時，代理需要反覆回去看同一個檔案、花更多詞元理解脈絡，但最終完成率差不多。雜亂程式碼不讓代理更笨，但讓它「走更多冤枉路」。

任務類型也有差異：集中在單一模組的任務（cognitive-hotspot type）受程式碼整潔度影響更大；跨模組的任務（multi-module type）差異相對小一些。

## 為什麼雜亂程式碼讓代理多走冤枉路？

研究者分析發現，在雜亂程式碼裡，代理更常在讀完一個檔案後需要再回頭讀。可能原因是：命名不清晰的函數讓代理誤判要找的邏輯在哪裡；深度巢套的邏輯讓代理在分析依賴關係時需要多個往返。對應地，乾淨程式碼中函數命名預測性強、單一職責原則讓代理一次就找到目標。

## 做不到的地方

- 六對倉儲、33 個任務的規模偏小，統計上能看到的效應可能受特定任務和倉儲特性影響
- 「整潔度」用 SonarQube 規則定義，這是靜態分析工具商的定義，不一定等同於所有工程師對「整潔」的理解
- 只測試了 Claude Code / Sonnet 4.6 一個代理，不同代理（如 Copilot、Cursor）可能對程式碼品質的敏感度不同
- 通過率差異不顯著也可能是因為任務設計本身，難度不夠高的任務容易讓兩種情況都通過

## 怎麼看這件事

這篇論文的結論很實用：如果你用 AI 代理幫你寫程式，讓程式碼保持整潔不是為了讓 AI 更聰明，而是為了讓它更有效率——直接影響 API 費用。每次試驗省 7% 聽起來不多，但在大規模 CI/CD 流水線或長期代碼維護任務中，累積起來相當可觀。

需要保留的懷疑：研究者本身是靜態分析工具的製造商，有動機去強調整潔程式碼的好處。雖然這篇論文的核心數據是誠實的（通過率無差異），但研究設計、指標選取和強調重點都值得獨立第三方重現驗證。
