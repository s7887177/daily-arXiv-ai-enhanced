# 用自然語言查詢時間序列資料庫：Sonar-TS 的「聲納式」搜尋驗證框架

> 原始論文：Sonar-TS: Search-Then-Verify Natural Language Querying for Time Series Databases
> 作者·單位：Zhao Tan、Yiji Zhao、Shiyu Wang、Chang Xu、Yuxuan Liang、Xiping Liu、Shirui Pan、Ming Jin（新加坡國立大學、香港城市大學等機構）
> arXiv：2602.17001v2 ・ 分類：cs.AI、cs.CL、cs.DB

一句話說重點：只要用自然語言描述想找的時間序列形狀（例如「先急跌再緩慢回升」），Sonar-TS 就能在龐大的時間序列資料庫中精準找出符合條件的時間窗口。

---

## 背景：「查資料庫」遇上「時間曲線」，現有工具兩頭不到岸

時間序列資料庫（TSDB）存著大量隨時間變化的數值記錄——股價、感測器讀數、伺服器指標、病患心電圖……這類資料龐大到用肉眼翻找不現實，非技術人員更難直接操作 SQL 查詢。

**現有自然語言查詢（NLQ）工具的困境：**
- **Text-to-SQL 方法**：擅長處理離散型、結構化查詢（「找出銷售額前十的商品」），但無法描述連續形狀（「找出先急跌後緩升的通道」）——SQL 根本就沒有「曲線形狀」的語法原語。
- **時間序列模型**：能辨識形狀，但要在數百萬筆歷史紀錄中全段掃描，計算量驚人，無法應對超長歷史資料庫規模。

## 怎麼做：像聲納一樣「先 ping 候選、再精確鎖定」

研究團隊提出 **Sonar-TS**，靈感來自主動聲納：先發出聲波（SQL 快速篩選候選窗口），再精確分析回波（Python 程式驗證原始信號）。整個框架分三個階段：

**階段一：離線資料預處理**
將原始時間序列轉換成多層「特徵表」（Feature Tables），涵蓋不同時間粒度（每日、每月、每年），並提取統計特徵與 SAX（Symbolic Aggregate approXimation，符號聚合近似）符號化表示。SAX 把曲線形狀轉成字串，讓標準 SQL 引擎能用正規表達式搜尋「形狀」。

**階段二：線上查詢——「搜尋—驗證」管線**
1. **任務規劃**：LLM 將用戶的自然語言問題拆解成有序子步驟清單（識別邏輯執行順序與所需運算元）。
2. **程式碼生成**：生成 SQL 查詢以在特徵表中快速 ping 候選時間窗口，再生成 Python 程式碼對原始信號做精確驗證，排除假陽性。
3. **經驗更新**：成功或失敗的查詢軌跡被存入經驗庫，透過「提示冷啟動」機制（Prompt Cold Start）持續精煉搜尋啟發式。

**階段三：後處理**
將執行結果（時間窗口、時間戳、純量值）轉成視覺化圖表與摘要報告，面向非技術用戶呈現。

## 結果

為了評估，研究團隊建立了 **NLQTSBench**——第一個面向 TSDB 規模歷史的大型自然語言查詢基準，含 1,037 道測試題，橫跨四個難度層次（基礎運算、形態識別、語義推理、洞察合成）。

- Sonar-TS 在四個難度層級上均顯著優於 Text-to-SQL、TSQA 模型和 Text-to-SQL + 相似度搜尋等基線。
- 特別在「形態描述」類查詢（如「快速下跌後長期平穩」）上表現突出，這是傳統 SQL 框架完全無法處理的場景。
- 搜尋—驗證的兩步架構有效降低假陽性率，相比直接生成 Python 對全歷史掃描快數個數量級。

## 做不到的地方

- 離線特徵表的構建需要事先設計特徵粒度，若時間序列的形狀模式超出預設粒度範圍，可能漏掉候選窗口。
- NLQTSBench 目前覆蓋的領域有限，在特定行業（醫療生理信號、工業感測器）的泛化能力待驗證。
- 系統依賴 LLM 進行任務規劃與程式碼生成，對開放域用語或模糊描述的容錯性有待測試。
- 實驗未報告在超大規模 TSDB（億筆以上）的查詢延遲表現。

## 怎麼看這件事

把時間序列「形狀化」成可以被 SQL 搜尋的符號，再用生成程式碼做精確驗證，這個「搜尋—驗證」思路本質上是把**計算成本分攤在兩個不同精度層次上**。快速 SQL 粗篩成本低但精度粗；精確 Python 驗證成本高但只針對候選窗口。這種分層設計對資料量特別龐大的資料庫是務實的工程折衷。對於需要從歷史感測器或財務資料中找特定形態事件的分析師來說，如果這個系統的界面夠友善，實用價值相當直接。
