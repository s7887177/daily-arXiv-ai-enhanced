# 科研資料庫的 AI 助理：既懂材料科學的行話，又守住你的資料隱私

> 原始論文：KadiAssistant: A conversational AI Agent for information retrieval in Kadi4Mat
> 作者·單位：Adrian Cierpka, Mohammad Shafiqul Islam, Johannes Steinhülb, Eric Dietriche Sesso Domtchoueng, Michael Selzer, Arnd Koeppe（德國卡爾斯魯厄理工學院）
> arXiv：2605.18850v1 ・ 分類：cs.IR / cs.AI

一句話說重點：這個系統讓研究人員用自然語言向材料科學資料庫提問，AI 助理會理解跨學科術語、尊重存取權限、而且整個 LLM 自架在機構內部不把資料送到外部雲端。

---

## 問題從哪裡來

電池研究是一個需要同時掌握電化學測量、材料表徵、物理模擬和製造參數的領域——每個子領域都有自己的術語、格式和標準。當這些資料全部存在同一個研究資料平台（如 Kadi4Mat）時，想找到一筆特定資料，往往需要同時精通這幾個領域的知識，還要熟悉平台的查詢介面，這對跨領域研究者而言是相當高的門檻。

更複雜的是**資料敏感性**。研究資料依生命週期可分三個溫度：剛產生的「熱資料」通常是私有的；進入分析階段的「溫資料」存取受限；已發表的「冷資料」才是公開的。一個 AI 助理必須在查詢時嚴格遵守這些存取權限——它能告訴你的，只能是你本來就有權看到的資料。

傳統上，商業 LLM 服務（如 ChatGPT）會在用戶對話時學習資料，這讓機構私有的研究資料面臨洩漏風險。

## 研究怎麼做

論文團隊開發了 **KadiAssistant**，整合到 Kadi4Mat 研究資料生態系統中，核心設計是三合一：

**自架語言模型（Self-hosted LLM）**：不把資料送到外部服務，整個 LLM 推論服務跑在機構自己的 GPU 伺服器上，資料不離開組織的邊界。

**語義相似性搜尋（Semantic Similarity Search）**：受 RAG（檢索增強生成）啟發，文件和記錄的元資料被切成小段（chunks），轉換成向量儲存。用戶提問時，系統將問題也轉成向量，找出最相近的文件片段，再交給 LLM 合成成答案。向量搜尋用的是近似 k-NN（k 個最近鄰居）演算法，搜尋結果再經過重排序（Reranking）服務過濾。

**嵌入 Kadi 的存取控制**：向量資料庫直接儲存在 Kadi4Mat 實例內部，而非獨立伺服器——這樣就能天然繼承 Kadi 的細粒度存取控制機制，不需要另外設計權限過濾層。當資料庫有更新（檔案新增、修改、刪除），系統會自動偵測並同步更新向量。

**AI Agent 架構**：KadiAssistant 不只是一問一答的聊天機器人，它是一個 Agent，能根據任務選擇不同工具——例如決定「這個問題需要語義搜尋」還是「直接查記錄元資料就夠了」，並維護對話歷史（儲存在用戶瀏覽器本地，不上傳伺服器）。

## 主要結果

論文以定性案例演示為主，展示了 KadiAssistant 在電池研究資料集上回答跨術語問題的能力（如「找出使用 LiFePO₄ 正極材料且操作溫度在 25°C 的實驗」）。系統能夠跨越不同研究者存儲格式的差異，整合分散的資訊。

程式碼已公開在 GitLab（論文中提供連結），可供其他機構部署自己的版本。

## 做不到的地方

- 論文未提供系統性的量化評估（如回答準確率、覆蓋率），主要以案例演示說明效果。
- 向量搜尋依賴語義相似性，若查詢使用不同學科的術語，可能找不到存在但描述方式不同的資料。
- 自架 LLM 需要機構有足夠的 GPU 資源，對小型實驗室可能是門檻。
- 對話歷史存在瀏覽器端，在多設備切換或共用電腦的場景下使用不便。
- 目前 Kadi4Mat 是相對小眾的科研資料平台，此系統的適用範圍受限於 Kadi 生態系。

## 怎麼看這件事

這篇論文解決的是學術界真實存在的痛點：多學科研究的術語壁壘 + 資料隱私的合規壓力。相比起要求研究者學習 API 或 SQL 查詢，「用自然語言問問題」的介面顯然更友善。

值得注意的是「把 LLM 跑在機構自己的 GPU 上」這個設計選擇——這在歐盟 GDPR 合規壓力下越來越重要。對機構資料主權有顧慮的場景，這篇論文的架構提供了一個可參考的範本，即使你用的不是 Kadi4Mat，其中的系統設計思路也有借鑑價值。
