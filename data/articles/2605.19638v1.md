# AI 一行指令生成輔助科技：障礙者使用數位工具的未來可以走多遠？

> 原始論文：The Accessibility Capability Boundary: Operational Limits and Expansion Potential of AI-Generated Browser-Native Accessibility Systems
> 作者·單位：Rizwan Jahangir（NUST，巴基斯坦）、Daisuke Ishii（Kiara Inc.，東京）
> arXiv：2605.19638v1 ・ 分類：cs.HC / cs.AI

一句話說重點：研究者提出「無障礙能力邊界」框架，分析 AI 生成的瀏覽器原生輔助系統能走到哪裡、卡在哪裡，並以一個為尼泊爾視障用戶實際部署的工具作為驗證。

---

## 為什麼無障礙設計至今還是個難題

「無障礙設計」聽起來像是理所當然的事，但現實中的數位世界仍然對許多障礙者充滿障礙。主要原因：傳統的輔助技術（Assistive Technology，AT）——如螢幕閱讀器、點字顯示器、語音控制——需要安裝、設定、需要系統管理員權限、需要技術支援，而且對使用者的語言和地區支援常常不足。

在資源有限的地區（如尼泊爾、印度農村），即使有網路，能安裝適合自己語言和環境的 AT 軟體幾乎是奢望。

大型語言模型（LLM）帶來了一個新可能：直接用自然語言描述需求，幾分鐘內生成一個跑在瀏覽器裡的客製化輔助工具——一個 HTML 單一檔案，零安裝，打開 URL 就能用。

## 無障礙能力邊界（ACB）框架

這篇論文的核心貢獻不是技術系統，而是一個**思考框架**——無障礙能力邊界（Accessibility Capability Boundary，ACB）。

作者把「無障礙」從「是/否的合規性」改成「一個多維度的能力空間」。每個輔助系統在這個空間裡有它能覆蓋的範圍（能服務哪些使用者、哪些環境），ACB 就是這個範圍的邊界。

系統的限制向量包含八個維度：
- **部署延遲**（Ld）：從需求到可用需要多久
- **認知負荷**（Lc）：使用者要記住多少操作步驟
- **基礎設施依賴**（Di）：需不需要外部網路或雲端計算
- **離線持久性**（Po）：斷網後能不能繼續使用
- **互動複雜度**（Cx）：完成一個任務需要幾個步驟
- **自適應性**（Ad）：能不能即時調整 UI 以符合個人需求
- **輔助技術相容性**（Ac）：和螢幕閱讀器等工具的相容程度
- **本地化覆蓋**（Lz）：是否支援用戶的語言和地區

## 瀏覽器原生 AI 工具的優勢在哪？

傳統 AT 在「部署延遲」（Ld）上表現差，但「離線持久性」（Po）可以做到完全本機；原生應用程式（Native Apps）在「自適應性」（Ad）上比傳統 AT 好；AI 生成的瀏覽器工具則把 ACB 在「自適應性」方向大幅外擴——因為用自然語言就能快速重新生成一個符合特定需求的介面。

論文用兩個實際案例驗證：
1. 為尼泊爾一位視障用戶用 Claude 生成的瀏覽器原生無障礙介面，支援語音輸出和鍵盤導航，在低頻寬環境可用
2. 開源的網路攝影機對齊助理（cam-guide-for-blind），用瀏覽器的 MediaDevices API 取得攝影機畫面，結合 Web Speech API 提供即時語音引導，幫助視障用戶對準鏡頭——全在瀏覽器內跑，不需安裝任何東西

## 做不到的地方

- **驗證難度高**：AI 生成的 HTML 是否符合 WCAG 無障礙標準，很難自動確認，人工測試仍難省略
- **離線持久性有限**：需要本機 ML 推論的功能（如電腦視覺）在低階硬體上跑不動
- **硬體接入上限**：點字顯示器、眼動儀等輔助裝置需要系統層級驅動，瀏覽器 API 碰不到
- **安全與隱私**：攝影機、麥克風存取需要用戶授權，瀏覽器環境的沙箱限制也制約功能範圍
- 論文的兩個案例是「探索性原型」，而非系統性使用者研究，結論主要是理論推導

## 怎麼看這件事

這篇論文的問題很有意思——「AI 生成的無障礙工具能走多遠？」——但它的答案更多是一個分析框架而非實驗結論。ACB 框架把一個模糊的問題結構化了，讓我們可以系統性地說「這類工具在哪個維度有優勢、哪個維度有硬限制」。

最真實的洞察是：對全球南方（Global South）的用戶來說，部署門檻常常比功能完整度更重要。一個 URL 可以開的工具，對需要管理員權限才能安裝 AT 的用戶來說，哪怕功能只有七成，也可能比功能十成但裝不起來的軟體更有用。這個角度值得無障礙設計社群認真對待。
