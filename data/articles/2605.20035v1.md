# 多模態大模型太貴跑不動？把畫面與聲音的 token 在不同層丟掉不同比例，省 9 倍算力還保 96% 效能

> 原始論文：Stage-adaptive Token Selection for Efficient Omni-modal LLMs
> 作者·單位：Zijie Xin、Jie Yang、Ruixiang Zhao、Tianyi Wang、Fengyun Rao、Jing Lyu、Xirong Li（中國人民大學、騰訊微信）
> arXiv：2605.20035v1 ・ 分類：電腦視覺・多模態大型語言模型

一句話說重點：能同時看影片、聽聲音、讀文字的「全模態大模型」（Qwen2.5-Omni、Qwen3-Omni）非常吃算力——非文字 token 數量遠遠超過文字。研究者觀察到一個現象：影像和聲音 token 的重要性「在不同層」很不一樣，越往後越冗餘。據此設計了不需要重訓的 token 篩選法 SEATS，**只保留 10% 的視覺與音訊 token，就能達到 9.3× 的 FLOPs 縮減、4.8× 的 prefill 加速，同時保住 96.3% 的原始效能**。

---

## 背景：影音 token 太多，模型跑不動

近年「全模態大型語言模型」（omni-modal LLM，下稱 om-LLM）像 Qwen2.5-Omni、Qwen3-Omni，能同時吃進影片、聲音、文字。它們的做法是把影片每幾秒切成「token」、聲音按時間切成「token」，跟文字 token 混在一起送進大型語言模型推理。

問題是這些非文字 token **多到嚇人**——一段幾分鐘的影片就可能產生幾千到幾萬個 token。LLM 的計算量隨 token 數量平方成長（attention 機制的本性），跑一次推論就會非常慢、非常貴。要把 om-LLM 部署到產品上（例如即時影音問答助理），「token 太多」是擋路的核心瓶頸。

## 既有作法的兩個盲點

過去有兩類 token 篩選方法，但都有缺陷：

1. **只針對視覺輸入**：只剪影片 token，不剪聲音 token。但 om-LLM 的算力都被「非文字 token 總和」吃掉，只剪一邊省得有限。
2. **進 LLM 前剪、固定比例**：在 token 進入 LLM 之前一次剪完，且每個模態的剪枝比例固定。例如「視覺剪 70%、音訊剪 70%」。問題是：**token 重要性會隨層數變化**，越深層越多 token 已經完成跨模態融合、可以丟掉，固定比例完全沒利用這個資訊。

## 關鍵觀察：影音 token 的依賴度會「逐層遞減」

研究者做了一個關鍵分析：他們去看「LLM 的每一層」對「視覺 token」和「音訊 token」的依賴有多少（用 attention 權重之類的訊號來量）。發現兩件事：

1. **依賴呈現「區塊狀」**——前面幾層密集、中間層中等、後面層稀疏。
2. **依賴整體隨深度遞減**——越往後，模型越少回頭去看影音原始 token，因為跨模態資訊已經融合到文字 token 裡了。

換句話說，**晚期層的非文字 token 大半是冗餘的**。這個發現自然導出他們的設計。

## 怎麼做：SEATS 三階段策略

SEATS（Stage-adaptive Token Selection）把篩選分成 LLM 進入前、進入後兩階段，後者再分三個階段（shallow / middle / late）動態調配：

**階段 0：進 LLM 前——空間時間去冗餘（winDivPrune）**

影片相鄰幀往往非常相似（你坐在桌前的兩秒前後幾乎沒變），聲音相鄰窗口也是。用「注意力加權多樣性選擇」先把這層冗餘消掉，等於壓縮輸入。

**階段 1：淺層（Shallow Layers, 1~Ls）——全部保留**

模型剛開始處理，每個 token 都還在做基本特徵抽取，這時候剪會傷大腦。全保留。

**階段 2：中層（Middle Layers, Ls+1~Lt-1）——查詢引導的預算分配**

模型開始做跨模態理解。每隔幾層做一次剪枝，依靠「查詢相關性分數」（query relevance scores）判斷現在這個時間窗口、哪個模態更重要——例如使用者問題如果是關於畫面的，就多保留視覺 token；如果關於對話內容，就多保留音訊 token。**剪枝預算是動態分配的，不是固定 50/50**。

**階段 3：晚層（Late Layers, Lt~L）——非文字 token 全砍**

跨模態融合已經完成，剩下的計算只需要文字 token 之間做高階推理。所有影像、聲音 token 一次砍光，後面幾層只跑文字。

整套方法 **完全 training-free**：不需要重新訓練 om-LLM，只是改變推論時 token 怎麼進進出出。

## 結果

在 Qwen2.5-Omni 和 Qwen3-Omni 上測試：

- **只保留 10% 的視覺與音訊 token**（極端壓縮）
- **9.3× FLOPs 縮減**
- **4.8× prefill 速度提升**（prefill = LLM 處理初始輸入那一步，通常是大頭）
- **保留 96.3% 原始效能**

這代表：原本要 10 秒才能跑完的問答，現在 2 秒就好，且答案品質只損失 4%。

這張圖讀法是「從左到右沿著一條管線走」。最左是三類 token（藍 = 視覺、紅 = 音訊、綠 = 文字）。**第一個剪枝點 winDivPrune** 在進 LLM 前，消除影音內部時間冗餘。接著 token 進入 LLM 的層堆疊：**淺層綠藍紅都不剪**；**中層每幾層做一次「query-guided 剪枝」**——根據使用者的提問內容，動態決定該保留哪一邊更多；**晚層直接把藍紅兩種非文字 token 全砍光**，只留綠的文字 token。最右邊 LM head 產生第一個輸出 token。整套策略呼應了論文核心觀察：**早期 token 都重要、晚期影音 token 都冗餘**。

## 做不到的地方

研究者實際上對限制著墨不多，從方法可看出幾點保留：

- **是 training-free 但有設計超參數**：每個階段的層數區間（Ls、Lt）需要設定，論文做了一些消融但部署到新模型上仍需調。
- **「查詢引導」需要查詢文字先進來**：純 token streaming（沒有提問，只是預先處理影音）時，動態分配缺乏指引，可能退化。
- **極端壓縮會傷某些任務**：保留 10% 才有 9.3× 加速，但效能落到 96.3%。對需要細節的任務（OCR 影片、複雜對話分辨）可能不夠。
- **沒測超長影片**：實驗用的影片長度落在 om-LLM 標準評估範圍內，長到幾十分鐘的影片是否仍然有效，未證明。

## 怎麼看這件事

**為什麼在意？** 多模態大模型的最大瓶頸不是「能力」而是「成本」——能聽能看的模型早就存在，但「便宜到能即時部署」這件事一直沒解決。9.3× 的算力縮減對產品落地是有實質意義的數字。如果你要做語音助理、影片問答機器人、智能客服，token 篩選這類「免費午餐」級的優化會直接決定產品能不能跑得起。

**哪裡該保留懷疑？** 96.3% 性能保留聽起來不錯，但 4% 的損失在某些長尾任務上會被放大。論文的標準 benchmark 之外，特定領域（醫學影像分析、安全監控、長對話）可能會吃到更大的傷害，要真正部署前還需自家測試。

**怎麼理解這個方向？** 這是 LLM 「推論優化」工具箱裡新加的一格：跟 quantization（量化）、KV cache 壓縮、speculative decoding 是同類的「不重訓也能省算力」技巧。對於要把大模型送進手機、邊緣裝置的場景，這類技術會持續被疊加使用。
