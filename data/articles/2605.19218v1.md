# 看圖 AI 記憶體爆炸怎麼辦？用旋轉對齊讓壓縮更聰明

> 原始論文：Rotation-Aligned Key Channel Pruning for Efficient Vision-Language Model Inference
> 作者·單位：Beomseok Kang、Dongwon Jo、Jiwon Song、Donghwee Son、Jae-Joon Kim（首爾國立大學）
> arXiv：2605.19218v1 ・ 分類：cs.CV、cs.AI

一句話說重點：在推理時壓縮視覺語言模型（VLM）的 KV 快取（Key-Value cache），以往方法要麼扔掉圖片 token（犧牲細節）、要麼壓縮特徵維度（效果差）；RotateK 用 PCA 旋轉讓特徵對齊，讓「少扔 token、多壓維度」成為一條兼顧精度和速度的可行路。

---

## 看圖 AI 為何特別耗記憶體

現代視覺語言模型（VLM）如 LLaVA、Qwen-VL，能同時理解圖片和文字。但圖片一進來就變成幾百到幾千個 token，比一段文字多出十倍以上。這些 token 在每一層 attention 裡都要存一份 Key 和 Value 矩陣——KV 快取——隨序列長度線性增長，讓 GPU 記憶體很快爆掉。

**主流解法是「token 剪枝」**：把「不重要」的視覺 token 直接丟棄。問題是：對於需要理解圖片整體細節的任務（如閱讀文件、精細定位），被丟掉的地方可能恰好是答案所在，無法挽回。

**RotateK 提出另一條路**：KV 快取的大小 = token 數量 × 特徵維度數量（通道數）。既然可以減少 token，也可以減少通道。在相同記憶體預算下，少扔一些 token、改為壓縮通道維度，就能保留更多視覺完整性。

## 為何通道壓縮之前做得不好？

Key 矩陣的通道重要性因 token 而異（token-dependent）——不同圖片區塊用到的特徵通道組合不一樣。

- **逐頭剪枝（head-wise pruning）**：為整個 attention head 決定統一保留哪些通道，實作簡單，但因為不同 token 的重要通道不同，一刀切誤差大。
- **逐 token 剪枝（token-wise pruning）**：每個 token 獨立決定保留哪些通道，精度好，但要存一個 O(L×d) 的遮罩矩陣，記憶體和 IO 開銷爆炸。

RotateK 的核心想法：**雖然 token 的重要通道在原始空間裡東一個西一個，但在對的旋轉基底下，它們會對齊到同一個低維子空間**。只要先做 PCA 旋轉，就能用輕量的逐頭遮罩（O(d) 大小）達到接近逐 token 剪枝的精度。

具體做法：
1. 計算查詢加權的協方差矩陣，找到最能保留 attention 分數資訊的主成分方向
2. 對 Key 矩陣做線上 PCA 旋轉（用 Cholesky 子空間迭代降低計算開銷）
3. 在旋轉後的空間做逐頭通道剪枝
4. 用自訂 Triton kernel 讓稀疏通道 attention 計算可以在 GPU 上高效執行

## 結果

在 LLaVA-NeXT-8B 和 Qwen2.5-VL-7B 兩個模型上，RotateK 與 FastV 和 VisionZip（純 token 剪枝基準）比較：

- 在相同 KV 快取記憶體預算下，加入 RotateK 的 token+channel 聯合壓縮，比純 token 剪枝在 TVQA、IVQA、CQA、DVQ 等多個任務上分別提升 4.3%~14.1% 精度
- 在 ChartQA 的精度-記憶體曲線上，RotateK 在每個記憶體預算點都高於純 token 剪枝基準
- 解碼延遲：結構化稀疏通道讓 Triton kernel 能直接在壓縮後的 Key 上運算，解碼速度有所提升（論文有詳細延遲分析）

## 做不到的地方

- RotateK 目前只壓縮 Key 矩陣，Value 矩陣壓縮尚未整合（理論上也可以壓縮 Value）
- PCA 旋轉引入了額外計算，在批次較小或序列很短的場景中可能抵消掉速度優勢
- 論文只在兩個 VLM backbone 上驗證；其他架構（如 Gemini 系列）效果待定
- 視訊等超長序列場景的效果尚未完整測試

## 怎麼看這件事

「在 GPU 上壓縮 AI 的記憶體使用」聽起來像純技術問題，但它直接決定了一個配備 8B 參數視覺語言模型的系統，能不能在有限資源的設備上（如消費級 GPU、邊緣計算）流暢處理高解析度圖片。

RotateK 的貢獻是找到了一個讓「精度」和「效率」之間的 Pareto 前沿往右上移動的方法：相同記憶體預算下保留更多有效資訊。這條「先旋轉再剪枝」的路徑也提示：與其在原始表示空間裡做壓縮，不如先找一個讓重要資訊集中的表示空間，再壓縮。這個想法可能在其他壓縮場景中也有啟發。
