# 每小時掃描數千份表單：把 AI 文件辨識從論文送進生產線的工程學

> 原始論文：Operationalizing Document AI: A Microservice Architecture for OCR and LLM Pipelines in Production
> 作者·單位：Yao Fehlis, Benjamin Bengfort, Zhangzhang Si, Vahid Eyorokon, Prema Roman, Patrick Deziel, Devon Slonaker, Steve Veldman, Ben Johnson, Joyce Rigelo, Michael Wharton, Steve Kramer（Kungfu.ai）
> arXiv：2605.18818v1 ・ 分類：cs.AI / cs.LG / cs.SE

一句話說重點：學術研究教你訓練模型，這篇教你把模型真的跑起來——每小時處理數千份多頁文件、成本從每頁一美分壓到十分之一美分，還保持 96% 準確率。

---

## 問題：模型訓練好了，然後呢？

學術界不斷產出更強的文件理解模型——LayoutLM、DocTR、Donut、Pix2Struct——每一個都在基準測試上刷新成績。但一個工程師想把這些模型部署到每天要處理數千份表單的系統，在文獻中幾乎找不到指引。

模型和生產環境之間有一道巨大的鴻溝：文件格式五花八門（多頁 TIFF、掃描 PDF、照片）、分類要把每份文件送到正確的萃取管線、光學字元辨識（OCR）要應付歪斜頁面和掃描雜訊、大型語言模型（LLM）要從中結構化地抽取欄位——這些操作分別屬於 GPU 密集、CPU 密集、IO 密集，彼此還需要協調。

## 怎麼做：三層微服務 + 非同步佇列

這篇論文描述的架構把整個管線拆成三個獨立微服務，部署在 Kubernetes 上：

**閘道器（Gateway）**：輕量的入口，只負責接受文件提交、把頁面圖像存入物件儲存（Object Storage）、在關聯式資料庫寫入追蹤記錄，以及把文件 ID 推入訊息佇列。閘道器刻意不做推論，讓它的故障模式單純——閘道掛了只是新文件進不來，飛行中的文件不受影響。

**工作節點（Worker）**：從訊息佇列拉取文件 ID，執行整個管線：分類 → OCR → 文字拼接 → LLM 結構化萃取。分類採用混合策略：先用本地 CLIP-KNN 模型快速篩選（97% 的案例在 0.5 秒內、成本 \$0）；只有信心度低於閾值（約 4%）才改送 VLM 雲端分類（2 秒、成本 \$0.01）。Worker 是 CPU 密集的編排層，刻意不持有 GPU。

**推論服務（Inference Service）**：獨立的 GPU 節點，只暴露 REST API，提供 OCR（DocTR）與 VLM（Claude Sonnet API 代理）能力。GPU 資源獨立水平擴展，不受 Worker 數量綁定。

非同步處理貫穿整個系統，讓大量 IO 操作（從物件儲存下載頁面、呼叫推論 API）不阻塞 CPU 資源。

## 結果：瓶頸在 OCR，不在 LLM

批次效能分析揭示了兩個出乎意料的發現：

1. **OCR 主導端到端延遲，不是 LLM 解析**：直覺上 LLM 是最貴的步驟，實際上 OCR 才是真正的時間殺手——因為掃描 PDF 的圖像品質問題，OCR 需要多次重試與 GPU 加速才能勝任。
2. **系統飽和點取決於 GPU 推論容量，不是 Worker 數量**：增加 Worker pod 超過某個閾值後吞吐量不再提升，因為推論服務的 GPU 已是共用瓶頸。

成本方面，最終把每頁成本從 \$0.01 壓到 \$0.001，同時維持 96% 準確率。

## 做不到的地方

這篇論文是經驗性的工程報告，不是受控實驗：缺乏與其他架構的量化對比基準，數字只反映 Kungfu.ai 自身的文件類型和工作負載特性，換成其他業務領域結果可能相差甚遠。敏感文件處理的安全隔離也只是設計原則的陳述，未提供驗證方法。

系統的核心設計如圖所示：Gateway 負責文件入口與追蹤，Worker 佇列負責 CPU 密集的管線編排，Inference Service（GPU）獨立提供 OCR 與語言模型推論，右側接入 Claude Sonnet（Anthropic API）處理需要語意理解的分類與欄位萃取。各層可獨立水平擴展，避免 GPU 資源被 CPU 編排的數量綁死。
