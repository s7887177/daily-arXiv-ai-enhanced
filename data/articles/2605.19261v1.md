# 網站自己修自己：讓 Web 應用在崩潰後 4 秒內自動復原的框架

> 原始論文：When Web Apps Heal Themselves: A MAPE-K Based Approach to Fault Tolerance and Adaptive Recovery
> 作者·單位：Sales Aribe Jr、Rov Japheth Oracion（菲律賓研究者）
> arXiv：2605.19261v1 ・ 分類：cs.SE / cs.AI / cs.HC / cs.PL

一句話說重點：把監控、分析、規劃、執行（MAPE-K 循環）加上自動修復模組組合起來，讓 Web 應用在服務崩潰、記憶體洩漏、資料庫斷線等故障時，平均 3.92 秒內自我恢復，比人工操作快了一半以上。

---

## 問題在哪裡

現代 Web 應用越來越複雜，但「故障處理」很多時候仍然靠工程師盯著監控警報、手動重啟服務。這樣做慢（人要反應時間）、貴（需要隨時有人值班），在高頻故障時根本跟不上。

已有的解法要麼是「只監控不修復」，要麼是靜態腳本（故障 A 就跑腳本 B），沒辦法從過去經驗中學習、改善自己的修復策略。

## 怎麼做

這篇論文提出一個模組化「自我修復框架」，核心架構是 **MAPE-K 迴圈**：

- **Monitor（監控）**：透過 Prometheus、ELK Stack、Grafana 即時收集 CPU 使用率、錯誤率、回應時間等遙測資料。
- **Analyze（分析）**：用 K-means 聚類、決策樹等機器學習方法偵測異常，F1-score 達 90.7%。
- **Plan（規劃）**：根據知識庫（K）中的歷史故障模式，選擇最合適的修復策略。
- **Execute（執行）**：由 **AutoFix 模組**自動執行恢復動作（重啟服務、釋放記憶體、重連資料庫等）。

知識庫會隨著每次修復結果更新，迭代學習哪種策略在什麼情境下最有效。

實驗在 Ubuntu 22.04 上注入了 20 種故障場景（服務崩潰、記憶體洩漏、資料庫斷線等），用 100 個並發用戶的 JMeter 負載進行評估。

## 結果

對比四種方法（見下圖）：

- 人工手冊（Manual runbook）：平均恢復時間 8.96 秒，成功率 90%
- 僅規則監控：6.42 秒，成功率 91%
- 僅協調器修復：5.37 秒，成功率 92%
- **本文框架**：**3.92 秒，成功率 93.2%**，系統吞吐量保留 94.8%

AutoFix 模組讓平均恢復時間（TTR）縮短了 56.2%。迭代學習讓修復效率在多輪循環後又額外提升了 18.6%。

## 做不到的地方

- 實驗在**單節點**環境運行，不是真正的分散式叢集，大規模部署的行為未知。
- 所有 20 種故障場景都是**預先設計**的，對全新類型故障（零日故障）的應對能力未測試。
- 研究者僅兩人，未有工業界合作夥伴或第三方驗證。
- 學習機制仍依賴預定義的修復策略，稱不上真正的「自主學習」。

## 怎麼看這件事

MAPE-K 框架在工業界（特別是雲服務、Kubernetes 環境）早有多種商業實現（如 AWS Lambda、Dynatrace），這篇論文的方向並不新穎，但針對「應用層」自我修復並且組合進反饋學習的整合做法，在學術文獻中算是一個完整的端到端示範。

對實務工程師而言，這篇更像是「概念驗證」而非「直接可用的工具」，因為預定義修復策略的局限在實際生產環境會很快碰壁。但如果你在思考如何設計自動化運維系統的架構邏輯，MAPE-K + AutoFix 的組合思路值得參考。
