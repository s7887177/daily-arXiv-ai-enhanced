# 真實世界的 API 會更新——AI 代理應試的「環境」憑什麼永遠不變？

> 原始論文：The World Won't Stay Still: Programmable Evolution for Agent Benchmarks
> 作者·單位：Guangrui Li、Xaochen Xu、Yi Liu、Ziwei Dong、Xingyuan Pan、Tianqi Zheng、Jason Choi、Michael J. Morais、Binit Jha、Shaunak Mishra、Bingrou Zhou、Chen Luo、Monica Xiao Cheng、Dawn Song（Amazon、UC Berkeley）
> arXiv：2603.05910v2 ・ 分類：cs.AI

一句話說重點：ProEvolve 讓 AI 代理的測試環境能夠「可程式化地演化」——增加工具、改掉 API 格式、廢棄舊功能——讓我們終於能測試 AI 在動態環境中的適應能力。

---

## 背景：你在考試場學的，在職場卻找不到

AI 代理（agent）的核心能力是呼叫工具完成任務：查詢資料庫、呼叫 API、下訂單。現有的測試基準（benchmark）幾乎都是「靜態」的：工具的介面固定、資料的 schema 不變、功能不增不減。

但現實中的軟體環境不是這樣的。以電商平台為例：上個月你的購物車 API 接受 `product_id`，下個月它改名為 `item_id`；原本的訂閱功能可能被整合到訂單系統；新的支付方式加進來，舊的被廢棄。每次版本更新，使用這個系統的代理都面臨新挑戰。

這意味著在靜態環境下評測的 AI 代理，其泛化能力是有疑問的：它只是「背住了某個版本的 API」，而不是真正學到了「如何在演化的環境中靈活應對」。但目前幾乎所有評測都做不到這件事，因為**讓環境「有規律地演化」本身就很難**：增加一個工具可能破壞十個測試；改一個 schema 會讓所有依賴它的任務變得不一致。

## 怎麼做：把環境當成一張圖，把演化當成圖的轉換

ProEvolve 的核心設計是一個**帶類型的關聯圖**（typed relational graph），用統一的結構表示整個工具調用環境：

- **節點**：資料實體（如「用戶」、「訂單」、「商品」）、工具（API functions）、Schema 定義
- **邊**：實體之間的關係（「訂單 belongs to 用戶」）、工具對資料的存取（「查詢訂單工具讀取訂單節點」）

在這個圖表示之上，**環境演化被定義為圖的轉換操作**：
- **新增工具**：在圖中加入新節點，連接它能讀取/修改的資料節點
- **廢棄功能**：移除特定工具節點，更新依賴它的邊
- **Schema 重組**：修改資料節點的屬性，自動傳播到所有依賴此 schema 的工具定義

這種形式化讓每一次「演化」都有明確的影響範圍，不會破壞未受影響的部分，也不會留下前後矛盾的定義。

**任務生成**：對於每個版本的演化環境，ProEvolve 從圖中隨機取樣子圖（subgraph），以子圖對應的資料和功能為基礎，生成具體的任務沙箱（sandbox）——每個任務有自己的前置條件（要求某些資料已存在）、用戶指令（「用我的信用卡建立一個訂閱」）和成功標準（「訂閱 ID 已建立且與訂單關聯」）。

## 結果：ProEvolve 產生高品質環境，揭露代理的弱點

論文在電商（e-commerce）和航空訂票（airline booking）兩個真實工具調用場景上驗證：

**品質驗證**：生成的演化環境通過了可執行性檢查（所有工具實際可調用）、實現合法性（生成的程式碼通過 lint 和單元測試），以及人工審核（語意一致性）。

**代理行為診斷**：將生成的基準應用於測試當前主流代理，發現：
- 某些環境版本讓代理的成功率大幅下降，定位了具體的「失敗模式」（如依賴已廢棄工具、無法適應 schema 變更）
- 「記憶固化」（memory-frozen）是常見問題：代理在環境演化後仍然嘗試使用舊版本的工具名稱或參數格式

**可擴展性**：ProEvolve 能系統性地產生數百個不同版本的環境，而不是手動設計每個版本，大幅降低了創建動態基準的成本。

## 做不到的地方

- **自動生成的任務品質上限有限**：基於圖取樣的任務生成方式，難以捕捉真實業務邏輯中的複雜語意和細微需求。
- **真實生產環境差異**：目前的演化類型（新增/移除/修改）涵蓋了主要模式，但真實軟體更新還有更多複雜情況（如向後相容的舊版 API 保留一段時間）。
- **小規模領域**：只在兩個領域（電商、航空）驗證，其他領域（醫療、法律、程式設計）是否適用未知。
- **沒有測試代理的學習能力**：基準評估的是代理在單一版本內的表現，沒有測試「代理跨版本學習適應」的能力。

圖示展示 ProEvolve 的完整流程，分為兩個階段。

**左側「環境演化」**：從種子環境 K（包含用戶、購物車、訂單、商品等節點的關聯圖）出發，通過語意演化意圖（如「新增訂閱功能」、「更新商品需求」），自動應用圖轉換操作，生成演化後的環境 K+1（在圖中新增了訂閱節點和對應的邊）。整個過程由三種角色的代理（系統架構師、產品經理、程式設計代理）協同完成。

**右側「任務生成」**：對演化後的環境，透過子圖取樣（subgraph sampling）和隨機遊走（random walk）識別出連通的功能子集，再生成具體的任務提示（如「為我的訂單建立一個訂閱」、「使用不同的支付方式」），以及對應的初始狀態和成功標準。右上角的 JSON 片段展示了一個具體的資料條目範例。

## 怎麼看這件事

這篇論文解決了一個基礎性的問題：**AI 代理的「測驗」和「真實工作」之間有一條靜態 vs. 動態的鴻溝**。靜態基準就像期末考試永遠考同一份試卷——頭幾次測對了不代表真的能力，只代表記住了那份卷子。

ProEvolve 提供了一個讓測試環境能夠「合理演化」的工具，往真實世界的複雜性邁進了一步。對 AI 代理的開發者而言，這類動態基準的意義在於：能更早發現代理的「記憶固化」問題，在部署到真實生產環境之前就修正。

下一步的挑戰是讓代理不只是「在任何給定版本上都能完成任務」，而是「在版本更新後能自我調適」——那才是真正意義上的代理智能。
