# 「她現在在哪？」多模態大模型在 3D 場景裡只能秒答一次，這篇想讓它記住

> 原始論文：LMM-Track4D: Eliciting 4D Dynamic Reasoning in LMMs via Trajectory-Grounded Dialogue
> 作者·單位：Chaoyue Li（華中科技大學）、Yongxue Xu（中山大學）、Jie Feng（北京航空航天大學）、Jiayu Ding（北京大學）、共同隸屬 InkMind.AI
> arXiv：2605.19390v1 ・ 分類：多模態大模型・4D 動態理解

一句話說重點:當你連續問「剛剛 0.8 秒投三分球的是誰？接著畫出他從 0.5 秒到 1.2 秒的 3D 軌跡」，多數多模態大模型會在第二個問題就把人「跟丟」；這篇蓋了一個專門考這種「跨輪對話＋3D 軌跡」的基準 **Track4D-Bench**，並設計了一個會「記住目標」的模型 **LMM-Track4D**，在 526 個對話樣本上把軌跡精度大幅拉開。

---

## 背景：影片問答 ≠ 真的看懂時空

ChatGPT、Gemini、Qwen-VL 這類「多模態大模型（LMM）」處理圖片或影片問答已經很強，但它們對「**4D 連續時空推理**」其實還是新手——也就是要在多個視角、多輪對話之間，**穩定記住「同一個目標」在不同時間點的位置**。

研究者用一個籃球場景示範這個落差：第一輪問「誰投了三分球？」，第二輪接「畫出他的 3D 軌跡」。表面上看起來只是兩個問題，但模型必須：

1. 把第一輪的「他」跟第二輪的「他」綁定成同一個球員；
2. 在被防守者遮擋的時刻仍然知道他在哪；
3. 跨幾秒鐘給出座標連續的 3D 軌跡。

目前主流模型大多把影片**逐幀拆成 tokens**，沒有「目標身份的記憶體」，所以一旦遮擋發生、或進入第二輪對話，模型就會出現「身分跳掉」「位置誤判」之類錯誤。

## 怎麼做：給模型加三個小零件

研究者沒有從頭訓練一個 9B 大模型，而是**凍結 Qwen3.5-9B 主幹**、用 LoRA 微調，外加三個自訂模組：

- **RTGE（Ray-Time Geometry Encoding）**:把相機的「視線方向 + 時間戳」直接編碼進視覺 token，告訴模型「這個 patch 是從哪台相機、什麼角度、什麼時間拍到的」。讓視覺 token 帶上幾何資訊。
- **TRK（state-memory token）**：一顆專屬的「**目標記憶 token**」。每輪對話結束後，這顆 token 帶著「我們剛剛在追的人是誰」這個隱狀態傳到下一輪，於是「他」就不會跨輪掉鏈子。
- **OSK-RA 解碼器**：負責把軌跡輸出成 3D 座標。它先用「多視角射線交集」算一個粗略錨點，再加上殘差修正——避免第一步預測誤差把後面整條軌跡帶歪。

訓練分三階段：先單獨練軌跡輸出穩定，再聯合練語言＋幾何，最後用 GRPO 做策略校準。

順帶他們蓋了一個基準 **Track4D-Bench**：從 APIDIS（籃球）、KITTI（自駕）、WildTrack（行人）三個資料集挑出 526 段對話樣本（23.5k 幀、7.5k 個物件標註），題目分五類：身份、軌跡、關係、動態趨勢、場景級。

## 結果：把開源 SFT 基線拉開一個身位

在 Track4D-Bench 主表上：

- 通用 GPT-4o、Gemini 2.5 Pro 的 CIDEr 大約 0.15-0.25，**根本不輸出 3D 軌跡**；
- 最強的同資料 SFT 對照 Qwen3.5-9B+SFT 的 CIDEr 0.451；
- LMM-Track4D 拿到 **CIDEr 0.698、SAcc@0.5 = 0.758、Traj-Acc@1.0 = 0.626**——是唯一同時把「語言品質」跟「3D 軌跡準度」都做好的模型。

消融顯示三個模組真的各有貢獻：拿掉 OSK-RA 解碼器，TAcc@0.5 從 0.619 掉到 0.425；拿掉 TRK 記憶 token，模型完全無法穩定產出結構化軌跡。歷史對話也很關鍵——「不給歷史」遠不如「給自己上一輪的回答」，再不如「給黃金歷史」（即提供 ground truth 歷史回答給當前輪），代表跨輪傳訊本身就是這個任務的核心難點。

這張圖把整個模型攤平給你看。**左下角**多視角 2D 影像進入 Vision Encoder，被 **Ray-Time Geometry Encoding（藍色框）** 加上「相機視線＋時間」的編碼，變成「視覺 token」往上送。**中間紫色**的 [TRK] tokens 是這篇的關鍵——每輪對話會掛上一顆「狀態記憶體」slot，分別記住 Player #6、籃球、Player #4，跨輪不會掉。**右側**橘色是文字 tokens。三股 token 一起餵進凍結的 Qwen3.5-9B 主幹，輸出語言答案（最上方紅框寫著「Player #6 dribbles right and releases a three-point shot at 0.8s. Trajectory: t1=[x1,y1,z1]…」），同時 **右側綠色 OSK-RA 解碼器** 把 [TRK] 狀態轉成 3D 軌跡座標。

## 它做不到 / 沒解決的

- 模型主幹固定 Qwen3.5-9B、LoRA 微調，未測試更大或更小規模的拓展性。
- Track4D-Bench 雖然涵蓋籃球、自駕、監控三個場景，但**仍是「策展過」的 clip**，不是真實連續長影片串流，實際部署能不能撐長時間沒有答案。
- 軌跡 horizon 固定 4 步，預測超過短時段的長期運動仍是未知數。
- 程式碼跟資料集承諾未來公開，目前 GitHub repo 尚未開放。

## 怎麼看這件事

**為什麼在意？** 自駕、運動分析、安防都需要「跨時間追同一個目標」這種能力。把它包裝成「對話＋軌跡」的形式，等於是給 LMM 加上一個未來必備的「短期工作記憶」零件——這跟 LLM 加 KV cache、加 scratchpad 的思路是同源的。

**哪裡該保留懷疑？** 整個系統高度依賴 [TRK] token 的隱狀態能跨輪「正確傳遞」目標資訊，但這顆 token 怎麼編碼、為何能穩、會不會在更多元場景下崩潰，論文沒給可解釋性的細節。Track4D-Bench 也偏向「乾淨的策展對話」，跟野生使用情境差距尚未驗證。

**怎麼理解這個方向？** 影片理解正從「**把影片當靜態 token 序列**」走向「**讓模型維護一個顯式狀態**」——這跟把 transformer 當有限狀態機、給它 memory tokens 的近年研究合流。LMM-Track4D 是把這個想法用在 3D 軌跡上的一個具體實作，方向比結果重要。
