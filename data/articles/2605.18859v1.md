# AI 代理每一步都要呼叫語言模型：怎麼智慧選擇「夠好又省錢」的那個？

> 原始論文：TwinRouterBench: Fast Static and Live Dynamic Evaluation for Realistic Agentic LLM Routing
> 作者·單位：Pei Yang, Wanyi Chen, Tongyun Yang 等多位作者（Gradient、蘇州大學、USC、CMU、上海交大、UC Berkeley、UCLA 等）
> arXiv：2605.18859v1 ・ 分類：cs.LG / cs.AI

一句話說重點：TwinRouterBench 是第一個針對「AI 代理任務中每一步呼叫」而設計的路由評估基準，用靜態離線和動態在線兩條賽道，測試路由器在決定「這步用便宜小模型，還是用貴大模型」時的真實效果。

---

## 問題在哪裡

現代 AI 代理（agent）系統——如 Coding Agent、Deep Research、電腦操控代理——完成一個使用者請求往往需要**幾十次甚至上百次**的 LLM API 呼叫：搜尋資料、生成程式碼、執行工具、驗證輸出……

每次都用最強大（最貴）的模型？費用難以接受。每次都用最便宜的模型？任務完成率大幅下降。「LLM 路由（LLM Routing）」的概念就是：**智慧地讓每次呼叫用剛好足夠好的模型，省下多餘的費用**。

但現有的路由基準有一個根本問題：**它們只在「一次問一個問題」的場景評測路由器**，完全忽略了代理任務中的特性：
- 每一步有豐富的「前文脈絡」（對話歷史、工具輸出、部分程式碼）。
- 當前步驟的路由決策錯誤，可能在幾步之後才顯現（選了便宜模型做錯一步，後面的任務全垮）。
- 評測時依賴線上 LLM 評審（又要花錢，又不可重現）。

---

## TwinRouterBench 怎麼做

**兩條互補賽道：**

**① 靜態賽道（Fast Static Track）**：「快速離線開發用」
- 970 個「路由器可見前文」片段，來自 520 個代理任務實例（SWE-bench、BFCL、mtRAG、QMSum、PinchBench 五個領域）。
- 每個前文附有「執行驗證過的目標模型級別（tier）」標籤——透過「降級-級聯（downgrade-and-cascade）」協議決定每步最低應使用哪個級別的模型。
- 評分完全是確定性的算術計算（不需要線上 LLM 評審），零成本、可重現。

**② 動態賽道（Live Dynamic Track）**：「端到端真實驗證用」
- 在 500 個 SWE-bench Verified 任務（軟體工程基準）上真正跑代理，每次 LLM 呼叫由路由器從「鎖定模型池（Low/Mid/Mid-high/High 四個級別）」選一個模型。
- 評測指標：任務解決率 + 實際 API 費用。
- 本文報告了 100 個樣本的保留集評測。

---

## 結果如何

基準本身是工具性貢獻，論文主要展示了基準的設計合理性，並用幾種基礎路由策略驗算：
- 靜態賽道的得分與動態賽道的任務完成率有相關性，說明靜態賽道可用於快速初步開發。
- 「總是用最高級模型」和「總是用最低級模型」的兩個極端，都分別在費用或成功率上有明顯缺陷。
- 不同任務類型（長文脈、程式碼、工具呼叫）對模型級別的敏感度不同，強調路由不是一個單一策略能搞定的問題。

---

## 做不到的地方

- 基準本身並不包含一個「最佳路由器」——它只是評測框架，需要社群來提交和比較不同路由方法。
- 動態賽道費用昂貴（真實 API 呼叫），對學術研究者來說進入門檻較高。
- 目前只覆蓋五個任務類別；醫療、法律、創意寫作等其他代理應用場景未涵蓋。
- 「鎖定模型池」的組成固定，難以直接遷移到不同 API 提供商或自部署模型的場景。

左側「靜態賽道」（紫色）包含五種代理工作負載（長文脈、程式碼、多輪對話、RAG、工具呼叫），評估用即時算術評分、零 API 費用；右側「動態賽道」（綠色）連結到真實的 SWE-bench Verified 任務，路由器從鎖定池（Low/Mid/Mid-high/High 四個費用級別）選模型，以任務解決率和實際 API 費用雙維度評估；中央的「開發-驗證循環」說明兩條賽道的互補關係——靜態快速迭代，動態最終驗收。

## 怎麼看這件事

AI 代理的普及讓「如何在每一步選對模型」變成一個真實的工程和經濟問題。現有路由基準只看一次性問答是個明顯的盲點，TwinRouterBench 填補了這個空缺。對想實際部署 AI 代理系統並控制成本的工程師來說，這個基準的出現是好消息；對研究者來說，它提供了一個設計清晰、評分可重現的比較平台。
