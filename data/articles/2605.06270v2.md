# 從千張影片重建 3D 場景一次提速 28 倍：訣竅是「**問問題的 token 不能省、答案的 token 可以狠壓**」

> 原始論文：Spark3R: Asymmetric Token Reduction Makes Fast Feed-Forward 3D Reconstruction
> 作者·單位：Zecheng Tang、Jiaye Fu、Qiankun Gao、Haijie Li、Yanmin Wu、Jiaqi Zhang、Siwei Ma、Jian Zhang（北京大學深圳電子計算機學院 + 北大計算機學院）
> arXiv：2605.06270v2 ・ 分類：cs.CV（電腦視覺）

一句話說重點：從一支千幀影片重建 3D 場景的 AI 跑得很慢、又無法走捷徑；研究者發現注意力機制裡「**問問題的 token**」與「**回答的 token**」對壓縮的容忍度天差地遠——把後者狠壓、前者輕壓，端到端速度直接提升到原本的 28 倍，重建品質幾乎沒掉。

---

## 為什麼這件事重要

從多張影像重建 3D 場景，是自駕、機器人、AR/VR 共同需要的能力。傳統做法（SfM、MVS）要逐場景優化，慢且貴。近兩年出現了「**前饋式 3D 重建**」這條路線（代表作 VGGT、π³、Depth-Anything-3 等）：一個 Vision Transformer，一次前饋就同時吐出每個畫素的深度、相機位姿、點雲——**不用任何後處理優化**。

**問題出在 attention 的二次方成本**：當輸入從幾張圖擴大到一支幾百／幾千幀的影片，全域注意力（global attention）成本爆炸性增加。1000 幀的影片基本跑不動。

過去的解法兩派：
- **串流（streaming）/分塊（chunk）**：逐幀或逐塊處理。省了，但跨幀的整體一致性下降。
- **Token 壓縮**（FastVGGT、LiteVGGT）：對所有 token 一視同仁地合併。能加速約 10 倍，再壓品質就崩。

## 他們的關鍵直覺

Transformer 的注意力分三類 token：**query（問問題的）**、**key（被搜尋的標題）**、**value（被取出的內容）**。3D 重建任務裡：
- **query token**：對應「**這一視角想知道哪些幾何資訊**」——非常**個人化**、不能跟別的 query 合併。
- **key-value token**：對應「**場景共享上下文**」——大量資訊跨幀**重複**、可以狠狠壓。

過去方法把這兩類同等對待，相當於「**讓最敏感的 query 跟著最容忍的 KV 一起被砍**」——結果限制了壓縮上限。

研究者做了一個關鍵實驗（見圖）：分別壓 query、壓 KV、兩個一起壓。藍線（只壓 KV）幾乎平的——壓 32 倍誤差幾乎沒變；橘線（只壓 query）一壓就垮；紅線（同時壓）最差。**證明兩類不對稱**。

## 怎麼做（Spark3R）

基於這個觀察，他們提出「**不對稱 token 壓縮（asymmetric token reduction）**」：

1. **Query token 用組內合併（intra-group merging）**：保留結構，輕度壓縮。
2. **Key-Value token 用輕量剪枝（lightweight pruning）**：狠狠壓縮，最高 32 倍。
3. **層自適應排程（layer-adaptive schedule）**：經驗顯示不同 attention 層對壓縮的敏感度不同——對不敏感的層用更大的壓縮率，敏感的層留多一點。

整套是「**訓練自由（training-free）**」的：直接插到既存的 VGGT、π³、Depth-Anything-3、VGGT-Ω 等預訓練模型上即可，**不需要任何重訓**。

## 結果

- 在 1,000 幀輸入下，**端到端速度提升最高 28 倍**，重建品質仍與原模型競爭。
- 跟過去單一壓縮率方法（FastVGGT ≈ 4 倍、LiteVGGT ≈ 10 倍）相比拉開一截。
- 跟 TTT-based 加速方法（VGG-T³、ZipMap）速度相近，但**完全免重訓**，後者要 100k 步 × 8 張 A100 起跳。

## 做不到的地方

論文以 ATE（絕對軌跡誤差，姿態的精度指標）為主要衡量，沒有特別突出細節重建品質的視覺評估。另外 1,000 幀的加速倍數受 GPU 記憶體與實際資料分佈影響。對於高度動態場景（場景內每個物件每幀都在變），KV token 共享上下文的假設未必成立——可能比靜態場景效率提升較小。

下方那三張小圖是論文最有說服力的視覺證據：同樣的壓縮率（16 倍），「**只壓 KV**」的重建幾乎跟原始無壓縮看不出差別；「**只壓 query**」就開始模糊；「**同時壓**」直接稀疏破碎。這就是 Spark3R 設計核心的視覺化證據。

## 怎麼看這件事

**為什麼在意？** 前饋式 3D 重建是讓 AR 眼鏡、自駕、機器人能即時掃環境的關鍵能力。如果 1,000 幀影片從跑不動變成 28 倍加速還能保品質，下游應用的部署門檻直接下降。

**哪裡該保留懷疑？** 「28 倍」是峰值數字，實務上加速倍數會隨硬體、batch、模型大小而異。論文沒有把實際下游應用（AR 即時重建、機器人 SLAM）的端到端體驗測一遍——理論加速跟工程體驗有時差距大。

**怎麼理解這個方向？** Transformer 在影像領域已經被各種「**找出哪些 token 是冗餘的**」研究系統性壓縮過很多輪。Spark3R 的價值在於「**指出過去方法忽略了角色不對稱**」這個觀察——這在影像、影片、3D 領域是個可移植的觀察。下一波可預期更多「**按角色拆解壓縮**」的研究，把 Transformer 壓得更扁。
