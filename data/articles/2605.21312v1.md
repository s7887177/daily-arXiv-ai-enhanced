# 大型語言模型的推論系統越來越複雜，工程師要怎麼在沙盒裡先「跑一遍」？

> 原始論文：Frontier: Towards Comprehensive and Accurate LLM Inference Simulation
> 作者·單位：Yicheng Feng、Xin Tan、Yangtao Deng、Yimin Jiang、Yibo Zhu、Hong Xu（香港中文大學）等
> arXiv：2605.21312v1 ・ 分類：cs.DC / cs.AI / cs.LG

一句話說重點：Frontier 是一個離散事件模擬器，能在普通 CPU 上逼真地模擬出現代 LLM 推論系統——包含推理、代理、強化學習這些複雜負載——平均輸送量誤差低於 4%，比現有模擬器準了一個數量級。

---

## 背景：LLM 推論系統越來越難懂，也越來越難優化

ChatGPT 這類大型語言模型在線上服務時，背後的系統複雜程度驚人。早期是「一個 GPU 跑完一切」，現在的生產系統已進化成多種部署型態：

- **Prefill-Decode Disaggregation（PDD）**：把「讀懂問題」（prefill）和「逐字生成回覆」（decode）分開，放在不同的 GPU 集群執行，讓各自的硬體使用率更高。
- **Attention-FFN Disaggregation（AFD）**：更細粒度地把「注意力計算」和「前饋網路計算」也分開到不同硬體。
- **複雜並行**：張量並行、流水線並行、專家並行（Expert Parallelism，用於 Mixture-of-Experts 模型）同時存在。
- **新型工作負載**：Chain-of-Thought 推理（讓模型思考幾百步再答）、AI Agent（多輪工具呼叫）、強化學習 rollout（讓模型自己探索答案再用於訓練）。

這些複雜組合導致一個問題：**在真正花錢買 GPU 跑之前，工程師幾乎沒有辦法準確預測系統的性能表現。** 現有的模擬器要嘛架構太舊（假設系統是一個整體副本，沒有分解），要嘛用的是「平均情況分析代理」（analytical proxy），在動態變化的負載下誤差很大。

## Frontier：三層架構的離散事件模擬器

這篇論文提出的 **Frontier** 是一個**離散事件模擬器**（Discrete-Event Simulator，DES）——模擬系統中每個有意義的「事件」（請求到達、批次開始、傳輸完成等），並追蹤系統在每個時間點的精確狀態，而不是用統計平均值估計。

Frontier 的架構分三個層次：

**1. 保真度平面（Fidelity Plane）**：負責預測「每個操作要花多久」的成本模型，包括計算成本（Comp.Op Libs）、通訊成本（Comm. Backend）和記憶體容量（Memory Capacity）。這些成本是用真實 GPU 的 profiling 資料拟合出來的，在「看過」的硬體上可以推廣到沒測試過的配置。

**2. 控制平面（Control Plane）**：管理整個模擬的協調——全域控制器、叢集工人（Cluster Worker）、副本工人（Replica Worker）、模擬事件驅動器（Sim. Event Driver）、以及指標追蹤器。整個排程邏輯在這裡運行。

**3. 執行平面（Execution Plane）**：在每個 Replica Worker 內部模擬一次完整的推論流程：請求佇列 → 排程器 → KV-Cache 管理器 → 批次引擎 → 模型執行。同時包含 Runtime Adapter，處理各種執行時期優化（CUDA Graph、Speculative Decoding、Block-Hash Prefix Cache、Chunked Prefill）。

## 關鍵準確度

在 16 台 H800 GPU 的真實測試台上：

- 平均**輸送量（throughput）誤差 < 4%**
- 共置（co-location）模式下，端到端延遲誤差從現有模擬器的 **44.9% 降到 6.4%**
- 分解（disaggregation）模式下，從 **51.7% 降到 2.6%**

Frontier 還可以在普通 CPU 上擴展到超過 1000 個 GPU 的叢集模擬，而且速度合理。

這張圖清楚呈現了三層結構。頂部的 **Workload & Config** 輸入了服務配置、模型設定、推論執行時配置和工作負載生成器（聊天、代理、推理）；箭頭指向右側的 **保真度平面**（Fidelity Plane），裡面預測計算、通訊和記憶體的成本。中間的**控制平面**（Control Plane）包含全域控制器，裡面有模擬編譯器（Sim. Complier）、指標追蹤器（Metric Tracker）、叢集工人、事件驅動器和多個副本工人（Replica Worker）。底部展開的**執行平面**（Execution Plane）則是每個副本工人的內部——請求佇列、排程器、KV-Cache 管理器、批次引擎、Runtime Adapter 層級，以及右側的傳輸觸發器（Transfer Trigger）處理分解架構下的跨節點傳輸。這三層的分工讓模擬器既能捕捉高層架構，也能精確模擬每個操作的時序。

## 做不到的地方

Frontier 的成本模型依賴在目標硬體上預先 profiling 的資料——如果要模擬一個自己沒跑過的新型 GPU，成本估計的準確度會下降。此外，雖然支援 1000+ GPU 的大規模模擬，但論文的真實驗證只到 16 張 H800，更大規模的模擬準確度尚未確認。目前也不支援異構網路（不同頻寬的互聯連接）。

## 怎麼看這件事

LLM 推論系統工程是當前 AI 基礎設施最熱門的領域之一。系統工程師的日常痛點是：想試一個新的 GPU 配置、新的並行策略、或新的排程政策，但每次實驗都要花費真實硬體成本和時間。Frontier 的意義是：提供一個**夠準確的沙盒**，讓工程師在真正投入之前先在 CPU 上快速評估不同方案。

更深遠的意義是：隨著 LLM 推論架構越來越複雜（從整體副本 → 分解 → 異構配置），單純依賴「跑一遍看看」的實驗驅動工程越來越昂貴。模擬工具有機會在系統設計的上游發揮更大的作用，縮短從想法到部署的循環。這篇論文在這個方向上提了一個有說服力的初步方案。
