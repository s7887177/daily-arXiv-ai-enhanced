# 讓機器人「對齊地圖」的老引擎，搬進 AI 框架後快了二十倍

> 原始論文：Bundle Adjustment in the Eager Mode
> 作者·單位：Zitong Zhan、Huan Xu、Zihang Fang、Xinpeng Wei、Yaoyu Hu、Chen Wang（紐約州立大學水牛城分校、喬治亞理工、普渡大學、卡內基美隆大學）
> arXiv：2409.12190v4 ・ 分類：cs.RO

一句話說重點：研究團隊把機器人定位與 3D 重建裡一個核心的數學優化步驟（束調整），重寫成能直接在 PyTorch 這個主流 AI 框架裡跑、又有 GPU 加速的版本，速度比業界老牌工具平均快約 18 到 23 倍，要寫的程式碼還更少。

---

## 背景：機器人怎麼知道自己在哪、東西在哪

機器人導航、AR、無人機建圖背後都有一個關鍵技術叫 **束調整**（Bundle Adjustment，簡稱 BA）。直白說，它做的是「對齊」這件事：機器人從不同角度拍了一堆畫面，BA 會反覆微調「相機在每個時刻的位置姿態」和「環境中每個 3D 點的座標」，讓它們跟實際拍到的畫面盡量吻合。它是「同時定位與建圖」（SLAM，邊走邊算自己在哪、邊畫地圖）的核心零件之一。

問題出在工具鏈。現在感知系統越來越依賴深度學習，主流框架是 PyTorch，它走的是 **「即時模式」**（eager mode）——你寫一行程式它就立刻執行，像寫普通 Python 一樣直覺、好除錯、好改。但業界最常用的幾個 BA 函式庫（GTSAM、g²o、Ceres Solver）都是 C++ 寫的，**不能原生接進 PyTorch**。這帶來三個痛點：

1. **不夠靈活。** 這些舊工具要求你「執行前先把運算流程圖固定死」（靜態圖），沒辦法在跑的途中根據中間結果動態調整——而像「剔除離群觀測值」這種操作，正需要依執行中的結果臨機決定。
2. **開發體驗差。** C++ 工具沒有 Python 那種互動式、好除錯的環境，研究者寫起來事倍功半。
3. **資料搬來搬去很慢。** 舊工具的優化跑在 CPU，神經網路跑在 GPU，兩邊資料不斷搬運，大規模問題下開銷很大。

## 怎麼做：用 PyTorch 重寫，但解決兩個硬骨頭

作者的目標是做一個「原生活在 PyTorch 即時模式裡」的 BA 函式庫。聽起來只是搬個家，但有兩個技術硬骨頭：

1. **稀疏感知的自動微分。** BA 裡每個觀測其實只跟「一個相機位置」和「一個 3D 點」有關，絕大部分組合是無關的（術語叫「稀疏」）。但 PyTorch 內建的自動求導只會算「稠密」版本——把所有輸出對所有參數的關係全算一遍，等於浪費海量算力去算一堆注定是零的東西。作者設計了一套「知道哪裡是稀疏」的求導策略，只算真正相關的部分。
2. **GPU 加速的稀疏線性代數。** BA 的核心是「二階優化」，需要解大型稀疏方程組。作者實作了專為這個場景設計、能在 GPU 上跑的稀疏運算。

成果是一個既保有 PyTorch 直覺好用、又能 GPU 加速的束調整函式庫。

這張圖把整篇的主張一目了然地畫出來。橫軸是「寫一個最小可運行範例需要多少程式碼」（用 token 數當與寫作風格無關的代理指標，越靠左越省事），縱軸是「跑完基準測試要多少時間」（秒，對數刻度，越低越快）。藍點是 C++ 老牌工具（GTSAM、Ceres Solver、g²o），黃點是 Python 工具。**本論文方法「Ours」落在最左下角**——同時做到「最快」和「最少程式碼」，標註明示比 GTSAM 快約 18.5 倍、比 Ceres 少寫約 26% 程式碼。左下角的綠色箭頭與「Lower is Better」提醒讀者：越往左下越好。

## 結果：平均快二十倍上下，準度維持

- **大幅加速。** 在所有基準測試上，相較 GTSAM、g²o、Ceres，平均加速約 **18.5 倍、22 倍、23 倍**；在大規模問題上甚至可達上百倍加速，同時維持高準度。
- **少寫程式碼。** 在公平比較的最小範例下，比 Ceres 少寫約 26% 程式碼。
- **能無縫接進深度學習流程。** 展示了它能整合進 iMatching、VGGT 等現代深度學習管線，提升訓練效率；在「自監督特徵匹配」等任務上也帶來明顯改善。
- **不只 BA，還能做姿態圖優化（PGO）。** 在 sphere 等資料集上，相比 Ceres，準度相當而速度大幅領先（某資料集從約 15 秒降到約 1.7 秒），顯示方法的通用性。原始碼已開源（github.com/pypose/bae）。

## 做不到的地方

論文很誠實地列出未竟之處：

- **目前偏向 GPU，CPU 沒優化。** 還沒導入多執行緒（Intel OneTBB）、SIMD 指令等 CPU 加速技術，純 CPU 場景未必占優。
- **記憶體開銷偏高。** Python 的自動垃圾回收和 PyTorch 的動態張量管理雖然方便，但比靜態編譯的 C++ 函式庫吃更多記憶體；作者建議用手動緩衝預配置、TorchDynamo 或 TorchScript 編譯來改善。
- **生態相容性與任務範圍仍待擴展。** 尚未支援 JAX、MLX 等其他框架，也還沒涵蓋機器人操作、運動規劃等更廣任務，以及更多損失函數與優化模板（如 dogleg、L-BFGS）。

## 怎麼看這件事

**為什麼值得在意？** 束調整是 SLAM、AR、攝影測量的底層引擎，而現代感知越來越離不開深度學習。把這個老引擎原生搬進 PyTorch、又能 GPU 加速，等於把「傳統幾何優化」和「深度學習」之間的接縫補平——對做機器人感知、3D 重建的研究者，這能大幅降低原型開發與除錯的門檻。

**哪裡該保留懷疑？** 亮眼的加速數字是在論文選定的基準上、且偏向 GPU 場景取得；記憶體開銷較高、CPU 未優化是真實代價。它的價值更多在「開發效率與整合性」，純看極限效能未必全面勝過高度優化的 C++ 工具。

**怎麼理解這個研究方向？** 這是「把傳統優化工具重寫進深度學習框架」這個整合趨勢的代表作。當系統同時需要傳統幾何與神經網路時，把兩者放進同一個框架、共享 GPU、共用自動微分，往往比讓它們各跑各的、不斷搬資料更有效率——這個「工具鏈統一」的思路，在機器人與科學計算領域正越來越重要。
