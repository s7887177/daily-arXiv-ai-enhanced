# 影像切割 AI 一直在做白工——拿掉這一步，邊緣裝置上快了一半

> 原始論文：Token-Space Mask Prediction for Efficient Vision Transformer Segmentation
> 作者·單位：Calvin Galagain、Martyna Poreba、François Goulette（Université Paris-Saclay CEA List、ENSTA Paris / Institut Polytechnique de Paris，法國）
> arXiv：2605.18177v1 ・ 分類：cs.CV

一句話說重點：很多影像「逐像素切割」的 AI 模型，內部其實是用一串「token」在運算，卻硬要先把它還原成一張大圖再算遮罩——這步是沿襲舊習慣的多餘動作；研究者證明可以直接在 token 上算，省掉它後，在 NVIDIA Jetson Orin 嵌入式裝置上運算量砍掉約一半、速度快約 45–55%，準確度幾乎不變。

---

## 背景／問題：沿襲舊習慣的一道多餘工序

**影像分割**（segmentation）是電腦視覺的核心任務：把畫面裡每個像素都標上它屬於什麼（這塊是路、那塊是行人、那塊是天空）。它對機器人、智慧監控等需要「即時看懂場景」的嵌入式系統很關鍵——但這些裝置算力、記憶體都很吃緊。

近年主流是用 **Vision Transformer**（ViT，一種把影像切成小方塊「token」再用注意力機制處理的模型）。其中「查詢式」做法很強：用一組可學的「查詢」去問「這張圖裡有哪些物件/區域」。

但作者點出一個怪現象：這些模型**內部明明是用一串 token 在運算**，最後預測遮罩時卻習慣性地先把 token「攤回」成一張密集的空間特徵圖、再放大解析度、再做空間運算。這套流程其實是**照抄更早的卷積網路（CNN）的設計慣例**，並不是 ViT 本質上需要的——而它帶來的額外記憶體佔用與延遲，正是即時嵌入式部署最痛的點。

打個比方：你心算就能得出答案，卻硬要先把每個數字寫成一張大表格、再從表格上一格格讀出來算——表格這步是多餘的，還很佔桌面。

## 怎麼做：直接在 token 空間算遮罩

作者提出 **TokenMask**，一個可以直接接在任何 ViT 骨幹後面的統一「遮罩頭」，同時支援語意/實例/全景三種分割：

- **不還原成大圖。** 直接用「查詢」和「patch token」之間的相似度算出遮罩分數（保留原本那套線性打分機制，沒有改變辨識能力），跳過「攤成特徵圖 → 特徵放大 → 空間點積」這一整段。
- **把放大挪到最後。** 原本的「放大解析度」是在高維特徵空間做（要對 C 個通道逐一放大，很耗）；TokenMask 改成等算出遮罩分數後，在**分數（logit）空間**才做插值放大——這時要放大的維度少很多，便宜得多。
- **省的不只是算術，更是搬資料。** 在嵌入式硬體上，記憶體存取常比算術更燒效能；TokenMask 避開了把大特徵圖寫進記憶體又讀出來的大量資料搬運，因此在實機上加速特別明顯。

這張圖左右並排對比兩種做法，方塊由上往下是資料流。**左邊 (a) 是傳統做法**：影像 → ViT 骨幹 → patch token，然後走藍色框那段「Token-to-Grid 還原成特徵圖 → Feature upsample 特徵放大（粉紅色塊，最耗的步驟）」，再做空間點積得出遮罩。**右邊 (b) 是本文 TokenMask**：一樣到 patch token，但直接算「Token-space scores（綠色塊）」，省掉了左邊那整段藍框的特徵圖還原與特徵放大；只在最後做一次便宜的「Logit upsample 分數放大（綠色塊）」。最下方兩行小字點出差別：左邊「reshape → 特徵圖 → 空間運算」，右邊「沒有特徵圖；用 token 分數直接出遮罩」。

## 結果

跨多個資料集（ADE20K、Cityscapes、COCO-Panoptic）、多種 ViT 大小、多種分割任務：

- 相較對照方法 EoMT，在 ADE20K 全景分割上，ViT-Tiny/Small/Base 的運算量（GFLOPs）分別減少 **53.6% / 48.0% / 44.4%**，在 NVIDIA Jetson Orin（嵌入式裝置）上最高加速 **+53.7%**；ViT-Large 也減 28.3%、加速 +15.9%。
- 準確度幾乎沒掉：全景品質（PQ）通常只變動 1.5–2.8 分以內。
- 相較更重的 Mask2Former / Segmenter，運算量最多省 **75–90%**、推理最多快 **2 倍**。
- 記憶體也明顯下降：ViT-Base 峰值配置記憶體從 763.6 MB 降到 499.2 MB，越大的骨幹省得越多。
- 在 COCO 與高解析度的 Cityscapes 上呈現一致趨勢，顯示「重組計算結構」而非犧牲辨識能力。

（補充：GFLOPs 是運算量、數字越低越省；FPS 是每秒處理張數、越高越快；PQ/mIoU/mAP 是準確度指標、越高越好。）

## 做不到的地方

- **不是純粹免費的午餐。** 準確度仍有「小幅但存在」的下降（全景品質約掉 1.5–2.8 分；某些設定下 mIoU 略降），追求極致準確度的場景需自行權衡。
- **只是換掉「遮罩頭」這一段。** 它沒有提出新骨幹或新訓練法，效益上限取決於既有 ViT 與既有打分機制；本質是工程上的結構重組與最佳化，非演算法上的突破。
- **驗證偏向效率面。** 重點在效率-準確度權衡與嵌入式硬體實測；對極端類別不平衡、特殊領域（醫療、遙測）等的泛化未深入探討。

## 怎麼看這件事

**為什麼值得在意？** 影像分割是機器人、自駕、智慧監控的基礎能力，而這些都跑在算力受限的邊緣裝置上。一個「不犧牲準確度、卻能砍掉一半運算與記憶體」的純結構改良，實務價值很高——同樣的硬體能跑更快、更省電。

**哪裡該保留懷疑？** 準確度終究有小幅下滑，不能說「完全沒代價」；而且這是「換掉一個模組」等級的改良，不是新範式。對精度極度敏感的應用要實測自己的資料再決定。

**怎麼理解這個研究方向？** 它體現了一個常被忽略的觀念：很多深度學習架構裡藏著「從前一代設計沿襲下來、但其實沒必要」的步驟。與其一味把模型做大，不如回頭審視「這一步是本質需要，還是歷史包袱？」——把多餘的工序拿掉，往往就是讓 AI 在真實裝置上跑得動的關鍵。
