# 把 AI 特工當成不可信任的程式碼來對待：從系統安全角度看 AI 代理的漏洞

> 原始論文：Agent Security is a Systems Problem
> 作者·單位：Mihai Christodorescu、Earlence Fernandes、Ashish Hooda、Somesh Jha、Johann Rehberger、Kamalika Chaudhuri、Xiaohan Fu、Khawaja Shams、Guy Amir、Jihye Choi、Sarthak Choudhary、Nils Palumbo、Andrey Labunets、Nishit V. Pandya（Google、加州大學聖地亞哥分校、威斯康辛麥迪遜大學、EmbraceTheRed、Meta FAIR、Gray Swan AI、康乃爾大學）
> arXiv：2605.18991v1 ・ 分類：cs.CR / cs.AI

一句話說重點：AI 代理的安全漏洞和歷史上的軟體安全問題如出一轍——「讓模型更強壯」不夠，必須把整個系統按「最小權限」、「信任邊界」、「資訊流控制」等幾十年前就確立的系統安全原則設計，才能從根本上防範攻擊。

---

## 問題出在哪裡

當 AI 代理能夠瀏覽網頁、讀寫檔案、呼叫 API、執行程式碼，攻擊者就有了新的攻擊面：在環境裡放入惡意內容，讓代理「被騙」執行危險操作。這類攻擊叫做**提示注入**（prompt injection）。

目前研究社群的主流應對方式是「讓模型更難被騙」——用對齊技術、安全微調、對抗訓練提升模型魯棒性。但這篇論文的作者——多位有幾十年系統安全經驗的研究者——指出這個思路的根本侷限：

> 同樣的問題在電腦視覺時代的「對抗性機器學習」（adversarial ML）就出現過，攻擊者總是能找到繞過模型防禦的方法。

他們的立場是：**AI 模型是不可信任的組件，就像作業系統不信任第三方程式一樣**。安全保障應該在系統層面強制實施，而不是寄望於模型本身。

## 幾十年系統安全的五大原則

論文梳理了傳統系統安全的核心原則，並討論如何應用到 AI 代理：

1. **最小權限**（Least Privilege）：代理只應擁有完成當前任務所必需的最低權限。如果任務是草擬一封電子郵件，代理不應該有執行任意 shell 命令的能力。

2. **TCB（可信計算基）防篡改**：系統的核心信任組件（記憶體、使用者資料庫、工具存取控制）不應被外部輸入所改變。

3. **完全中介**（Complete Mediation）：每一個跨越信任邊界的請求都必須經過安全策略的審查，不允許任何例外。

4. **安全資訊流控制**（Secure Information Flow）：敏感資訊的流向必須被追蹤和限制——即使代理有「存取」某個資料的權限，也不代表它能把那個資料送到外部服務。

5. **人類弱連結**（Human Weak Link）：人類操作員是安全架構的薄弱環節，系統設計必須預設人類會犯錯（誤點允許、設定過寬的策略等）。

## 11 個真實攻擊案例分析

論文分析了 11 個已發生的真實 AI 代理攻擊，包括：

- **ChatGPT 長期記憶 SpAIware**：透過提示注入污染 ChatGPT 的「記憶」功能，讓系統持續把用戶對話資料送到攻擊者伺服器。
- **Claude Code 資料外洩**：惡意提示隱藏在程式碼檔案中，指示 Claude Code 讀取 `.env` 環境變數（含 API 金鑰）後，用允許清單內的 `ping` 命令透過 DNS 查詢把資料外送。
- **Devin AI 開放埠**：代理把本應限制存取的埠對外暴露。
- 還有 Microsoft Copilot 資料外洩、DeepSeek 帳號接管、Cursor AgentFlayer 等。

幾乎所有攻擊都同時違反了「最小權限」和「安全資訊流控制」兩個原則——這不是偶然，而是這兩個原則在 AI 代理系統中最難實施的現狀反映。

## 研究挑戰

論文指出三大尚未解決的研究難題：

1. **分離指令與資料**：傳統系統靠 NX 位元（不可執行記憶體）或 SQL 預備語句（prepared statements）阻止資料被當成指令執行。但 LLM 的 context window 天然混合了信任的指令和不信任的資料，沒有硬體級別的分離機制，現有的「提示格式標記」方案被反覆繞過。

2. **最小權限沙箱＋可驗證策略生成**：傳統程式的權限是靜態的，可以事先審查。但 AI 代理執行的任務動態多變，每次對話的需求不同，策略需要動態生成——如何保證自動生成的策略符合安全意圖，並做到形式化可驗證，是開放問題。

3. **語義層的資訊流追蹤**：傳統資訊流控制在程式碼層追蹤資料標籤，但 LLM 把所有輸入混合成語義特徵，無法直接識別「這段輸出源自哪個輸入」。在 AI 模型中追蹤資訊流需要全新的方法。

## 做不到的地方

- 這是立場文章，不提供具體技術實作，每個原則的落地方案都仍是開放問題。
- 幻覺、協同作弊、存在風險等問題被刻意排除在外（定義為「AI 安全」而非「系統安全」範疇），論文範圍有清楚限制。
- 幾十年前系統安全的解法（如沙箱、IFC）在 AI 代理這個規模下的計算和工程成本尚未充分評估。

## 怎麼看這件事

這篇論文最有價值的部分，是用一句話概括了現有 AI 代理安全研究的根本問題：**把模型當成完全信任的核心，而不是一個可能行為異常的組件**。

幾十年前，作業系統研究也面過同樣的問題：「把 C 程式寫得更嚴謹、更難被攻擊」，不如「在沙箱裡跑、給最小權限、限制系統呼叫」來得有效。AI 代理現在走的路，和早期應用程式安全研究走過的彎路驚人地相似。

對於使用或開發 AI 代理工具的人，這篇論文提供的最直接啟示是：在設計代理系統時，把「代理能做什麼」的邊界設計得越具體越好——不要因為方便就給代理超出任務所需的廣泛工具存取權限。
