# GPU 記憶體不夠用，同時跑多個大語言模型有多痛？實測告訴你

> 原始論文：Towards Multi-Model LLM Schedulers: Empirical Insights into Offloading and Preemption
> 作者·單位：Mert Yildiz、Pietro Spadaccino、Alexey Rolich、Francesca Cuomo、Andrea Baiocchi（薩皮恩薩羅馬大學）
> arXiv：2605.19593v1 ・ 分類：cs.AI / cs.DC

一句話說重點：當 GPU 記憶體不夠同時塞進多個大語言模型時，把部分層卸到 CPU 或強制中斷重新排程的代價遠比直覺認為的更高、更不規律，這篇論文提供了第一批系統性的實測數據。

---

## 問題背景：多模型共享 GPU 是現實需求

現實中，企業和研究機構越來越少只跑一個大語言模型（LLM），更常見的情況是在同一批 GPU 上同時服務多個大小、架構、用途各異的模型——有的專門寫程式碼，有的擅長推理，有的多模態。

現有的推理框架（如 vLLM）主要為單模型優化，透過連續批次（continuous batching）和 KV 快取管理來最大化 GPU 利用率。但一旦切換到多模型場景，兩個重要機制的代價就變得難以預測：

- **CPU-GPU 卸載（Offloading）**：把一部分模型層放在 CPU 記憶體，只有需要時才搬回 GPU，讓超過 GPU 容量的大模型也能跑起來。
- **強制中斷（Preemption）**：當更高優先級的任務需要 GPU 資源時，暫停當前任務、釋放 GPU 記憶體、等高優先級任務完成後再恢復。

這篇論文就是要用實測回答：這兩種機制的代價究竟是什麼形狀？

## 主要發現

**1. 卸載代價是非線性的，且因模型而異**

作者在兩張 GPU（RTX 5000 Ada 和 RTX A6000）上，對 Llama3:8B、Qwen3:32B、Llama2:70B 三個模型，系統測試了「GPU 層數佔比」從 0% 到 100% 時的解碼吞吐量（tokens/second）。

關鍵結論：
- 卸載導致的吞吐量下降**不是線性的**，在某個臨界點之前（約 70-90% 層數在 GPU 上），性能下降相對平緩；但一旦 GPU 比例降到這個閾值以下，性能就急劇崩潰。
- **小模型更脆弱**：Llama3:8B 從 100% 到 90% GPU 層數時吞吐量幾乎不變，但到 80% 以下就驟降；相比之下 Llama2:70B 因為本身很慢，卸載的相對代價反而更分散。
- **輸出長度影響卸載性能**：長序列（5000 tokens）對卸載更敏感，因為每次卸載的記憶體移動量更大。

**2. 中斷恢復的代價主要在「重載模型權重」**

作者設計了受控的中斷實驗：讓一個任務在推理途中被暫停，然後恢復，記錄暫停-恢復的總時間。

發現 KV 快取的遷移（把中間推理狀態存起來）代價相對次要；**主要代價是把模型層重新搬回 GPU**。這意味著搶占的代價與模型大小高度相關，而不只與當前請求的序列長度有關。此外，不同 GPU 之間（PCIe 頻寬差異）和不同模型之間，中斷代價差異顯著。

**3. 排程器設計的啟示**

這些發現對下一代多模型排程器有直接意義：排程決策不能只看當前 GPU 使用率，還需要考慮：
- 每個模型在當前 GPU 比例下的卸載敏感性曲線
- 中斷後重載的代價估計
- 互連頻寬對資料移動的放大效應

## 做不到的地方

- **單 GPU 設定**：實驗基於單 GPU 配置，多 GPU 多節點的行為可能更複雜。
- **只測試了三個模型**：樣本偏少，不同架構（如 MoE 模型）的行為可能差異更大。
- **未提出具體排程演算法**：這是一篇「現象刻畫」論文，提供了 guidelines 但沒有附上新排程器。
- **負載模式固定**：實驗使用單一使用者請求，真實系統中並發請求的互動可能產生不同結果。

## 怎麼看這件事

這篇論文的貢獻在於把「多模型共享 GPU 時排程有多難」這件事，從直覺層面推進到實測數據層面。卸載代價的非線性特性，以及中斷代價主要來自模型權重重載這兩個發現，對系統工程師設計實際排程邏輯有直接參考價值。

它的局限性也很清楚：這是一個觀察性研究，不是一個解決方案。真正的多模型 LLM 排程器還有很長的路要走，但這批實測數據至少讓後來者可以用更準確的代價模型做設計決策，而不是憑感覺猜測 CPU-GPU 邊界在哪裡。
