# AI 幫你重構程式碼，但它引入的新 bug 有誰在管？

> 原始論文：Quality and Security Signals in AI-Generated Python Refactoring Pull Requests
> 作者·單位：Mohamed Almukhtar、Anwar Ghammam、Hua Ming（University of Michigan-Flint）
> arXiv：2605.21453v1 ・ 分類：cs.SE、cs.AI

一句話說重點：研究者分析了 438 個由 AI 代理人（GitHub Copilot、Cursor、Devin 等）自動送出的 Python 重構 PR，發現平均 22.5% 的改動有改善程式碼品質，但同時 24% 的檔案引入了新的程式碼規範問題，4.7% 帶來了新的安全疑慮——而且大多數 PR 仍被開發者接受合併。

---

## AI 越來越會送 Pull Request 了

你有沒有看過這樣的情景：GitHub 上突然有個 PR 從機器人帳號提交，說「我幫你重構了一些程式碼，讓它更簡潔」？這已經不是科幻小說，而是每天真實發生在許多開源專案裡的事。

GitHub Copilot、Cursor、Devin、OpenAI_Codex 等 AI 編碼工具越來越能不只是「建議程式碼片段」，而是直接**提交完整的重構修改請求**（Pull Request, PR）到真實的程式碼倉庫。這引出一個很實際的問題：**這些 AI 送的重構改動品質怎麼樣？安全嗎？**

## 研究怎麼設計的

美國密西根大學弗林特分校的研究者使用了 AIDev 資料集，從中篩選出 438 個由 AI 代理人提交的 Python 重構 PR，分布在多個真實 GitHub 開源倉庫中。

他們用兩層工具評估每個 PR 的影響：

1. **PyQu**（Python Quality 工具）：用機器學習模型評估五個品質屬性的變化——可理解性（Understandability）、可靠性（Reliability）、可維護性（Maintainability）、可用性（Usability）、模組性（Modularity）

2. **Pylint + Bandit**：靜態分析工具，Pylint 檢查程式碼規範問題（命名慣例、行長、縮排等），Bandit 檢查潛在的安全漏洞（例如使用不安全的函數、硬編碼密碼等）

## 主要發現

**好消息：AI 重構確實有改善效果，可用性最顯著。** 平均而言，22.5% 的改動讓至少一個品質屬性得到改善，其中可用性（Usability）改善最頻繁，達到 36.5%——這對應到「讓程式碼更容易使用、介面更清晰」這類改動。

**壞消息：問題同時被引入。** 24.17% 的被修改檔案出現了新的 Pylint 問題，主要是慣例層級的違規（如行太長、命名不符合 PEP 規範）。更令人擔憂的是：4.7% 的檔案出現了新的 Bandit 安全警告。

**更壞的消息：開發者大多接受了這些 PR。** 73.5% 的分析 PR 被合併，包括那些引入了新的規範問題或安全警告的改動——開發者通常不仔細 review 這些細節，或者認為這些是可接受的代價。

**不同 AI 代理人表現不一樣。** OpenAI_Codex 提交了最多 PR（354 個），在可靠性改善上表現較好；Cursor 在可理解性上改善率最高（34/99, 34.3%）；Claude_Code 的樣本數太少（每個品質屬性只有 7 個），不具代表性。

最明顯的視覺特徵是：**「可用性」這一列整體偏深**（OpenAI_Codex 達到 133/354 = 37.6%），代表可用性是 AI 最容易改善的面向。而**「模組性」這一列最淺**（各代理人改善率都在 10% 以下），代表讓程式碼更好模組化是 AI 重構最難達到的目標。

另一個值得注意的是 Claude_Code 的行——數字都很小（0/7 或 1/7），這不是說它表現最差，而是研究數據中它的樣本數極少，百分比計算意義不大。

## 這篇研究建立了一套「24 種重構操作分類法」

研究者從觀察到的 PR 差異中，整理出 24 種 AI 重構最常見的操作類型，並對應了每種操作最容易引發哪類 Pylint 或 Bandit 問題。例如：

- **移除 assert 語句**（Remove assert）：常對應到安全工具的警告，因為 assert 在生產模式可能被優化器忽略
- **用動態執行取代靜態邏輯**（Replace Code with Dynamic Execution）：帶來 Bandit 最多警告，因為動態執行（eval、exec）是常見的注入風險
- **移除未使用的 import**：通常是正面改善，減少 Pylint 規範問題

## 現在還做不到的事

- 研究的 438 個 PR 僅來自 AIDev 資料集，可能無法代表所有真實 AI 重構行為的分布
- 品質工具（PyQu）是機器學習模型，本身存在預測誤差，Pylint 和 Bandit 也有已知的誤報率
- 研究沒有追蹤這些 PR 合併後是否真的造成了生產環境問題
- Claude_Code 樣本數過少，無法得出有效結論

## 怎麼看這件事

**為什麼重要？** AI 代碼生成工具正快速滲入真實的軟體開發流程，而大部分討論集中在「AI 能不能寫對功能」，這篇把問題延伸到「AI 重構的程式碼在品質和安全上有沒有系統性的盲點」——這是更接近實際開發風險的問題。

**哪裡要保留？** 438 個 PR 在「大規模經驗研究」的標準下規模偏小，而且不同 AI 代理人的樣本數差異懸殊（OpenAI_Codex 354 個 vs Claude_Code 7 個）。另外，「被合併」不等於「沒問題」，開發者有時接受 PR 是因為懶得 review，這個「接受率 73.5%」的意義需要謹慎解讀。

**更大的脈絡：** 這篇研究的出現時機很有意思——恰好是 AI 編碼助理從「補全工具」升級為「自主代理人」的過渡期。當 AI 可以自己發 PR，負責任地評估這些 PR 的品質和風險就變成了一個工程管理問題，而不只是技術問題。這篇提出的分類法和工具流程，可以作為「AI 代碼審查守門員」的起點。
